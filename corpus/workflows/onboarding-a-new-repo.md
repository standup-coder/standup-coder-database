# 工作流：接手一个陌生仓库

新人最常见的第一个任务：在陌生仓库里开始干活。直接让 agent 改代码，等于闭眼开车。按下面五步走，30 分钟内建立足够动手的心智模型。

## 步骤

### 1. 自己先读三样东西（5 分钟）

README、目录顶层结构（`ls` 一层就够）、最近的提交（`git log --oneline -20`）。目的是知道：项目自称是什么、代码在哪、最近在忙什么。

### 2. 让 agent 跑起来（5 分钟）

> "这是 <项目路径>。目标：在本机把它跑起来。先列出你需要的步骤再执行；遇到环境问题给出最小修复，不要顺手改代码。"

跑不起来也要拿到"卡在哪一步"的结论，这本身就是重要信息。

### 3. 让 agent 画一张结构地图（10 分钟）

> "通读代码，输出一份结构说明：入口文件 → 主要模块及职责 → 模块间依赖方向 → 配置加载方式。每个模块给一个代表文件路径。控制在 60 行内。"

**人工检查点**：拿这张地图抽查 2-3 个文件，验证 agent 没有编造。地图错了后面全错。

### 4. 找到你要动的那个模块（5 分钟）

> "我要改 <功能>。从入口开始追踪这个功能的调用链，给出：涉及文件清单、每处的职责、有没有测试覆盖。不要改任何代码。"

### 5. 建立安全网（5 分钟）

- 跑一遍现有测试，记录基线（哪些本来就红）。
- 开分支，确认 `git status` 干净。
- 这时候才用[任务拆解](../../skills/task-decomposition/SKILL.md)开工。

## 常见坑

- **跳过第 3 步的人工抽查**：agent 的结构描述看起来永远很自信，编造与事实的差别只有抽查能发现。
- **在第 1-4 步就让 agent 顺手改代码**："顺手优化"会让你的改动和它的改动混在一起，没法 review。
- **忽略测试基线**：不知道哪些测试本来就红，最后会把"本来就坏"当成"你改坏的"，浪费一轮轮排查。
