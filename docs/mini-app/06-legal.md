# 小程序法律与合规

OPC 做小程序，法律部分的真实成本不是"打官司"，而是**上线前那几道门**：备案、类目资质、隐私政策、软著。这四件事任何一件没做，前面的开发全部白费。本篇按"义务 → 材料 → 周期 → 后果"组织，技术上怎么配一律在 [02-development.md](./02-development.md)。

## 1. 上线前合规清单

**【专题补写】** 按"不做会怎样"排序，前四条任一条缺失即无法上线或无法对外服务：

```
□ 小程序备案已完成，备案号已取得
    不做 → 上架与对外服务受阻；周期以周-月计，必须最先启动
□ 服务器域名已 ICP 备案，且主体与小程序主体一致或有关联
    不做 → request 域名校验失败，真机上接口全部失败（技术表现见 02）
□ 隐私政策文本已就绪，且覆盖 PIPL 要求的八项要素
    不做 → 触发隐私接口授权失败，且属合规硬伤
□ 用户协议单独一页，主体名称与联系方式与隐私政策完全一致
    不做 → 封号、UGC 归属、AIGC 标识无处约定，事后举证困难（见 7.6）
□ 账号注销与数据删除入口已实现（平台无此能力，必须自写）
    不做 → 删除权无法行使，是违规通报的高频项（见 6.5）
□ 类目选择与实际功能一致，需要的资质已上传
    不做 → 硬阻塞，改类目再提审，周期重算
□ 软著已申请（至少受理通知书）
    不做 → 分发/备案环节会被卡
□ 名称与简介无绝对化措辞、无"官方""国家级"等禁用词
    不做 → 拒审，甚至被认定虚假宣传
□ 第三方依赖的许可证已扫一遍，图标/字体/分享图素材商用授权可出示
    不做 → 见 5.2、5.3、5.4；素材与依赖在提审与投诉时都会被要求出示
□ 涉个人信息的接口全部走"单独同意"，无默认勾选、无捆绑授权
    不做 → 处罚案例见本篇第 6 节
□ 若有 UGC/评论/社区：内容审核机制与举报入口已实现
    不做 → 平台运营规范红线
□ 若有 AI 生成内容：算法备案与内容标识已处理
    不做 → 见第 6 节 AIGC 清单
□ 若售卖预付卡/次卡/会员：退款规则与经营者义务已明确
    不做 → 见第 11 节
□ 为小程序引流的付费合作内容已标"广告/推广"
    不做 → 内容侧违规连带小程序主体记分（见 9.6）
□ 接单做外包：合同已含成果归属、变更收费、逾期违约金
    不做 → 见第 10 节
□ 接内容/推广单：八要素已逐条落到书面，修改次数与发布时间已约定
    不做 → 见 10.1 的两份骨架对照
```

> **【专题补写】** 本清单为整合编排，条目依据见本篇各节来源标注。

## 2. 小程序备案与 ICP 备案：两件事，别混

**【专题补写】** 仓库原文把两者都叫"备案"，实际是两个独立义务，主体、入口、审核方都不同：

| | ICP 备案 | 小程序备案 |
|---|---|---|
| 备案对象 | 你的**域名/服务器** | 你的**小程序这个产品** |
| 触发条件 | 小程序要请求自建后端 | 小程序上线对外服务 |
| 审核方 | 省级通信管理局（经服务商代备案） | 省级通信管理局 |
| 与对方的关系 | 小程序备案通常以主体已完成备案为前提 | 域名未备案则后端接口不可用 |
| 用了云开发 | 无需自己备案域名 | **仍需小程序备案**（见下） |

> 上一条是本篇最重要的判断：`wechat.md:196-199` 说云开发"无需域名和备案"，它免的是**域名 ICP 备案**，免不掉 2023 年起的产品备案义务。二者不可互相推导。

### 小程序备案（2023 年起）

```bash
# 备案背景：
# - 工信部要求：国内 App 需进行备案
# - 类似网站的 ICP 备案
# - 2023 年开始分阶段实施

# 备案流程：
# 1. 准备材料：
#    - 企业营业执照
#    - App 负责人信息
#    - App 基本信息
#    - 隐私政策
#    - 软件著作权
# 2. 提交备案：
#    - 通过工信部备案系统
#    - 填写 App 信息
#    - 上传材料
# 3. 审核：
#    - 省级通信管理局审核
#    - 周期：1-2 个月
# 4. 备案号：
#    - 获得备案号
#    - 需在 App 中展示
```

**【专题补写】** 对 OPC 的三个实际结论：

1. **材料里的"隐私政策"和"软件著作权"是前置依赖**，意味着备案不是最后一步，而是排期起点。正确顺序：注册主体 → 域名+隐私政策 → 软著提交 → 小程序备案 → 开发并行 → 提审。**备案必须在开发期间就启动**，否则开发完成要空等 1-2 个月。
2. 上述材料清单写的是"企业营业执照"。个人主体小程序能否备案、以何种身份备案，仓库尚未覆盖，见"需你复核的事实"。
3. 备案信息变更（主体、名称、负责人）需重新走变更流程，不是改个字段。**改名前先想清楚**：名称一旦变更，可能连带触发重新审核。"回退到历史版本"与"改了重新提审"这两条流程在 [02-development.md](./02-development.md) 的"版本更新与回退"一节，发布节奏与止血顺序在 [03-operations.md](./03-operations.md)。

> 来源：`../super-individual/app-publishing-guide/common/version-number.md:230-263`

### ICP 备案

```bash
# ICP 备案：
# - 国内网站/App 服务器的必要资质
# - 工信部颁发
# - 证明网站合法运营

# 备案要求：
# 1. 主体：企业或个体户（个人网站部分限制）
# 2. 材料：营业执照（企业）、法人身份证、域名证书、服务器租赁合同
# 3. 流程：服务商代备案，或直接通过工信部

# 备案号展示：App 中需展示 ICP 备案号，并链接到工信部查询
```

小程序侧对域名的四条硬性约束（**必须 ICP 备案 / 备案主体与小程序主体一致或有关联 / 必须 HTTPS / 支持二级域名**）是法规义务，逐条的字段位置与配置动作全部归 [02-development.md](./02-development.md) 的"服务器域名与业务域名"，本篇不复述配置。这里只留合规侧的判断：

**【专题补写】** 第 2 条是 OPC 最容易踩的：域名用个人身份或前公司身份备案、小程序注册在个体户/公司名下，主体不一致会被要求整改。买域名和买服务器时就用**将来要注册小程序的那个主体**，事后转移备案主体成本远高于事前对齐。

> 来源：`../super-individual/app-publishing-guide/common/version-number.md:265-300`；`../super-individual/app-publishing-guide/mini-program/wechat.md:165-173`

## 3. 类目与资质：决定你能不能上

```bash
# 部分类目需要资质：
- 医疗：医疗机构许可证
- 金融：金融牌照
- 教育：教育资质
- 视频：视听许可证
- 新闻：新闻许可证
```

常用类目全表（原文摘录，社交类明确标注需资质）：

```bash
# 工具类：
- 工具（通用）
- 效率
- 生活服务

# 电商类：
- 电商平台
- 商家自营
- 快递服务

# 内容类：
- 资讯
- 书籍阅读
- 视频

# 社交类：
- 社交（需资质）
- 社区
```

> 来源：`../super-individual/app-publishing-guide/mini-program/wechat.md:343-377`

**【专题补写】** 原文只有一行资质清单，这里补上 OPC 真正需要的判断方式：

```
选类目三步判断：

第一步  按"实际功能"选，不按"想要的流量"选
        工具型小程序选内容类目，一旦被识别功能与类目不符 → 拒审且需重改
        反过来，为了绕开资质而选到宽松类目，属于"类目挂靠"，
        是平台运营规范里的典型违规，比拒审严重（后果见第 9 节）

第二步  先看资质能不能拿到，再决定做不做这个方向
        医疗机构执业许可证、金融牌照、视听许可证、新闻许可证都不是个人
        或个体户能取得的。这类方向对 OPC 实际不可进入 —— 这是产品选题
        阶段的结论，不是提审阶段的意外

第三步  确认同类目是否还要求"其他材料"
        部分类目除许可证外还要求 ICP 许可证、行业承诺函、主体性质限制
        （仅企业可上），仓库尚未覆盖具体清单
```

类目与商业的耦合点（费率与变现能力按类目开放，价与费的归属在 05）：

- 能否开通支付、能否开通流量主，与类目和主体类型都有关；**个人主体既不能开通微信支付，也不能开通流量主**（能力边界见 [02-development.md](./02-development.md)，费用口径见 [05-monetization.md](./05-monetization.md)）。
- 页面内容也受类目约束：类目决定可展示的功能范围，超出类目的内容在页面里出现即为不符（对页面内容的影响见 [01-design.md](./01-design.md)）。

> **【专题补写】** 三步判断法为编排补写；`wechat.md:368-377` 仅给出五类许可证名称。

### 版号：为什么"先做小程序"是一条合规策略

原文在讲 App 版号时给出 OPC 的分阶段策略，第一条就是把微信小程序当免版号验证场：

```bash
# 1. 早期验证阶段：
#    - 先做微信小程序
#    - 不需要版号
#    - 快速验证产品

# 2. 海外优先：
#    - 先上 Google Play
#    - 海外版不需要国内版号
#    - 验证商业模式

# 3. 工具类切入：
#    - 优先做工具类 App
#    - 软著即可发布
#    - 避免版号需求

# 4. 后续扩展：
#    - 产品验证后补齐资质
#    - 申请软著
#    - 考虑版号申请
```

同一份原文的风险规避部分给了反向约束：

```bash
# 1. 不要先上国内版：无版号可能面临下架、法律风险
# 2. 不要轻视：政策趋严、处罚力度加大
# 3. 合规运营：及时备案、资质齐全、内容合规

# Q: 软著和版号可以同时申请吗？ A: 可以，两者独立审批。
# Q: 个人开发者需要版号吗？     A: 理论上需要企业主体，建议咨询专业机构。
# Q: 版号申请被拒怎么办？       A: 根据审批意见修改后重新申请。
```

> 来源：`../super-individual/app-publishing-guide/common/version-number.md:305-357`

**【专题补写】** 这段策略挪到小程序语境要用得更精确，因为它同时是**选型约束**：

```
不含游戏玩法的工具/内容/服务类小程序  → 不涉及版号，原文策略直接适用
带游戏玩法的小程序（微信小游戏等）     → 版号义务大概率被触发，
                                        且小游戏在仓库里零覆盖，
                                        不要把"小程序不需要版号"当成通用结论
```

对 OPC 的实际含义：**如果你的产品有排行榜、关卡、抽卡、虚拟货币这类玩法，"先做小程序绕开版号"这条路径不成立**。选题阶段就要决定：去掉玩法做成工具（可上线），或保留玩法按游戏资质排期（版号周期以月计且个人主体不具备申请资格，见上引 FAQ）。仓库对"小游戏版号/资质要求"的具体条文尚未覆盖，这一项按最保守口径处理：**先不提玩法，玩法验证留到版号路径明确之后**。

> 政策快照｜截至 2026 年 10 月。版号审批口径与小游戏资质要求会调整，立项前请核对国家新闻出版署与平台方最新要求，以官方为准。

## 4. 软件著作权：国内分发的隐形门票

### 4.1 为什么要软著

```bash
# 软著是软件开发者对软件作品依法享有的专有权利。
# 国内大多数应用商店分发要求提供软著证书。

# 为什么需要（分平台要求）：
# - 华为 AppGallery：必须
# - 小米应用商店：必须（受理通知书可先上）
# - OPPO 软件商店：必须
# - vivo 应用商店：必须
# - 腾讯应用宝：必须
# - 百度手机助手：必须
# TapTap、酷安等可先上后补
```

> 来源：`../super-individual/app-publishing-guide/common/software-copyright.md:13-27`

**【专题补写】** 小程序与 App 的差异要分清：上面这份清单是**应用商店对 APK 的要求**。对小程序，软著的直接作用是 **2023 年备案材料清单里的一项**（见第 2 节 `version-number.md:249`），此外在侵权维权、后续上架 App、以及对外报价时作为权属凭证。**"小程序要不要软著"这个具体问题，仓库尚未覆盖**，以平台与主管部门当前要求为准。

### 4.3 材料与流程：两份原文里唯一不冲突的部分

个人申请材料清单：

```bash
# 1. 软件著作权申请表
#    - 软件名称（中英文）
#    - 版本号
#    - 开发完成日期
#    - 权利取得方式
#    - 联系人信息
# 2. 软件说明书
#    - 功能介绍 / 技术特点 / 使用说明
#    - 不少于 20 页
# 3. 源代码（前 40 页 + 后 40 页）
#    - 每页不少于 50 行

#    - 注意版权注释

企业申请把"身份证明"替换为营业执照复印件、法人身份证复印件（有代理人时再加代理人证件）。

# 步骤四 提交审核：确认材料完整 → 提交 → 等待受理 → 受理后进入审查

```

> 来源：`../super-individual/app-publishing-guide/common/software-copyright.md:66-102,375-430`

**【专题补写】** 上面两份清单在**页数上自相矛盾**：材料清单写"前 40 页 + 后 40 页"，法律专题那份写"前后各 30 页"（见 4.2 对照表）。按**页数多的一端**准备（40 页），少准备不会被判合格、多准备只是多几页。除此之外有三个只有自己动手才会遇到的坑：

```
说明书凑够 20 页     不是写文档，是"图文结合"：每个功能一页截图 + 一段说明，
                    小程序 8-10 个页面 + 登录/支付/设置流程即可达标。
                    设计稿与真机截图同时留档，别用模拟器水印图。
源代码前后各 40 页    每页 50 行意味着约 4000 行的有效代码量。
                    太小的项目（几百行）会被要求补交；生成物与依赖不要打进
                    提交范围，只交自己写的业务代码，且文件头部别留着他人版权声明。
开发完成日期         这是申请表上的自填字段，会成为将来维权的口径锚点。
                    它必须与你留存的 Git 历史一致 —— 填一个"想当然"的日期，
                    等于主动制造一份能被对方用来推翻权属的矛盾证据。
```

> 政策快照｜截至 2026 年 10 月。登记材料格式与页数要求以中国版权保护中心当期公告为准。

### 4.4 软著的法律效力：别高估

> **权属初步证据，非权利取得要件。**

**【专题补写】** 这句话的实际含义：软件著作权**自动产生**于开发完成之时，登记只是给争议时提供一份证明。因此：

- 不登记 ≠ 没有权利，但维权时举证成本高；
- 登记 ≠ 拿住了不可推翻的权利，对方可用"你没写过这段"抗辩；
- 真正的自我保护是**过程证据**：Git 提交历史、设计稿时间戳、内部记录。把这几样留好，比多一本证书有用。代码托管与提交记录本身即证据链（GitHub 私有库、内部 Git 均可）。

## 5. 商标、开源许可与素材授权

### 5.1 商标

```bash
# 注册流程：
# 查询 → 申请 → 形式审查（约 1 个月）→ 实质审查（4-6 个月）
#      → 公告（3 个月）→ 注册证

# 类别选择：
# - 第 9 类（计算机软件）：必注册
# - 第 42 类（软件服务/SaaS）：必注册
# - 第 35 类（广告、商业经营）：强烈建议
```

> 来源：`../legal/ip-protection-guide.md:122-131`

**【专题补写】** 全程粗算 **8-10 个月**。这决定了商标不是"上线前准备"，而是"上线后立刻启动、且先把名字占了"。真正影响上线的是**名称冲突**：小程序名称重名与侵权投诉由平台处理（处置见第 9 节），商标未下证不代表不能改名规避风险。所以顺序是：先做商标查询与第 9/42 类申请 → 再定小程序名称 → 备案/提审。名称含"官方""旗舰店"等字样的额外限制见第 9 节虚假宣传条目。

> 政策快照｜截至 2026 年 10 月。商标审查周期随商标局积压量浮动，"8-10 个月"是把形式审查 1 个月 + 实质审查 4-6 个月 + 公告 3 个月相加的粗估，实际以当期进度为准。

### 5.2 开源许可证传染性

```bash
# 企业诉求 → 推荐许可证
| 最大化传播，不限制使用   | MIT / Apache 2.0 | 无传染性，商业友好       |
| 要求衍生作品开源         | GPL 3.0          | 强传染，保护开源生态     |
| 网络服务也需开源         | AGPL 3.0         | 堵住 SaaS 漏洞           |
| 库被调用不传染，修改需开源| LGPL           | 平衡商业使用和开源贡献   |
| 专利保护 + 宽松使用      | Apache 2.0     | 含明确专利授权条款       |
```

对小程序最关键的一行是 **AGPL**：小程序是"网络服务"形态，引入 AGPL 依赖会触发"网络服务也需开源"义务。**你不想把源码公开，就要在引入阶段排除 AGPL**，而不是发布后补救。

GPL 防范的工程做法：

```bash
# - 通过 IPC 隔离 GPL 组件（独立进程调用，链接层面隔离）
# - 开源组件准入审批
```

> 来源：`../legal/ip-protection-guide.md:87-102,172-180`

许可证分三档看，第一档"宽松"并不等于"随便用"，第三档连"开源"都不是：

```bash
# Copyleft 许可证（强/弱著佐权）
| 许可证        | 传染性 | 特点                     | 代表项目            |
| GPL-2.0      | 强     | 衍生作品必须同许可        | Linux Kernel       |
| GPL-3.0      | 强     | 增加反 Tivo 化、专利条款   | GCC, GIMP          |
| AGPL-3.0     | 最强   | 网络使用也触发开源        | MongoDB(旧), Grafana |
| LGPL-2.1/3.0 | 弱     | 库链接不传染             | Qt, glibc          |
| MPL-2.0      | 文件级 | 修改的文件需开源，新文件不受限 | Firefox, Terraform |

# 源码可用但非开源（Source Available）
| 许可证             | 限制                 | 代表项目                |
| BSL 1.1           | 商业使用需付费，N 年后转开源 | MariaDB, Redis(2024 后) |
| SSPL              | 提供 SaaS 需开源全部服务栈  | MongoDB(2018 后)        |
| CC BY-NC          | 禁止商业使用            | 部分文档/数据集            |
| Elastic License 2.0 | 禁止托管服务           | Elasticsearch(2021 后)  |
| 木兰宽松 PSL-2.0   | 类似 Apache-2.0，中国法律适用 | OceanBase              |
```

> 来源：`../open-source-communities/oss-license-guide.md:27-45`

**【专题补写】** 这一节上面那张"企业诉求 → 推荐许可证"表里有**一句对 OPC 有误导性的话**：`无传染性，商业友好` 描述的是**你此刻拿到的那一版**，不是这个项目的永久承诺。同一份开源指南里的两个案例正是反例：

```bash
# Redis 许可证变更（2024）
# - 从 BSD-3 变更为 RSALv2 和 SSPLv1 双许可
# - 不再符合 OSI 开源定义
# - Linux 基金会 fork 出 Valkey 项目（BSD 许可）
# - 启示：源码可用 ≠ 开源，社区可能 fork

# Elasticsearch 与 SSPL
# - 2021 年从 Apache-2.0 转为 SSPL + Elastic License
# - AWS fork 出 OpenSearch（Apache-2.0）
# - 2024 年回归 AGPLv3 + 商业双许可
# - 启示：许可证变更可能催生竞争对手
```

> 来源：`../open-source-communities/oss-license-guide.md:185-203`

结论落到实操只有一条：**"MIT 所以可以放心用"是错的，"我锁死的那个版本是 MIT 所以可以放心用"才对。** 因此：

1. **锁版本**：`package-lock.json` / `pnpm-lock.yaml` 必须进仓库，别用 `latest` 或宽松 range 引入运行时依赖。
2. **别自动升大版本**：升级前重看该版本 LICENSE 文件，Redis/Elasticsearch 这类变更都发生在大版本上。
3. **弱传染也要读条文**：LGPL 的"链接不传染"有条件（可替换链接、保留归属），MPL 的"文件级"意味着**你改过的那个文件必须开源**——把库源码复制进小程序仓库改一改，是最容易踩的形态。
4. **中国主体优先看木兰**：木兰宽松许可证（MulanPSL-2.0）适用中国法律、含专利条款，是国内主体的第三选择，不只有 MIT/Apache 两条路。
5. 双许可项目（社区版 GPL + 企业版商业许可）不要指望"我用社区版没事"，商用条款以商业版合同为准。

### 5.3 开源合规流程与工具

```bash
# 五步流程：
# 1. 准入审批：引入开源组件前评估许可证兼容性
# 2. SBOM 管理：维护软件物料清单，记录所有依赖及版本
# 3. 定期扫描：CI/CD 流水线集成许可证扫描
# 4. 合规发布：按许可证要求附带声明、源码或 NOTICE 文件
# 5. 贡献管理：员工对外贡献代码需经内部审批（CLA 签署）

# 审计工具：
| FOSSA  | 商业 SaaS  | 自动化扫描、许可证合规、漏洞检测 |
| Black Duck | 商业   | 企业级 SCA，深度代码片段匹配     |
| Snyk   | 商业+免费层 | 开发者友好，CI/CD 集成          |
| ScanCode | 开源     | 免费，许可证和版权检测            |
| OWASP Dependency-Check | 开源 | 侧重安全漏洞            |
```

**【专题补写】** OPC 不需要这套企业级流程。最小可行版本只有两条：**（a）** 用 `ScanCode`（开源免费）或在 `package.json` 层人工过一遍许可证；**（b）** 直接排除 AGPL、GPL 与"非商业使用"类许可。上面这张工具表的价值是知道存在什么，不是让一个人公司去装 Black Duck。

> 来源：`../legal/ip-protection-guide.md:182-198`

一个人公司能落地的版本 —— 开源审计工具与"合规必备文件"：

```bash
# 依赖审计工具（开源可用的三件）
| license-checker | 开源 | npm 依赖许可证检查 | Node.js 项目 |
| go-licenses     | 开源 | Go 依赖许可证      | Go 项目     |
| Scancode        | 开源 | 全面的许可证检测引擎 | 自建合规流水线 |

# 合规必备文件
1. LICENSE 文件：项目根目录放置完整许可证文本
2. NOTICE 文件：Apache-2.0 要求，列出第三方归属
3. 版权声明头：源文件顶部添加版权和许可声明
4. CHANGELOG：记录许可证变更历史
5. 依赖清单(SBOM)：Software Bill of Materials，列出所有依赖及许可证

# 合规流程
代码引入 → 许可证识别 → 兼容性检查 → 审批流程 → 归档记录
定期审计 → 依赖更新 → 许可证变更检测 → 重新评估
```

> 来源：`../open-source-communities/oss-license-guide.md:106-133`

**【专题补写】** 上面五条"必备文件"里，**小程序只需要做两件半**（小程序是网络服务形态，不做二进制分发，NOTICE 与源码公开的强度远低于 App/库场景）：

```bash
# 1. 一条命令把依赖许可证列干净（引入新依赖前后各跑一次）
npx license-checker --summary
npx license-checker --onlyunknown     # 抓作者没写许可证的包 —— 风险最高的一类

# 2. 把输出存成仓库里的依赖清单，就是最小 SBOM
npx license-checker --json > deps-licenses.json
#    作用：将来出现许可证纠纷时，你能证明"当时这个包是 MIT"

# 3. 半件：README 里一段"第三方开源组件"列表（组件名 + 许可证 + 用途）
#    流量主/类目审核不会查，但被投诉时这是你最便宜的一份证据
```

两件要**排除**的东西：`--onlyunknown` 抓出来的无许可证包（无许可证 = 默认保留所有权利，不是"随便用"），以及任何 AGPL/GPL 的**运行时**依赖。构建期工具（打包器、lint、测试框架）不受小程序分发触发，不必过度洁癖。

### 5.4 素材商用授权：字体、图标、图片

**【专题补写】** 这一类是三端审核**不会拦、下证后索赔最狠**的区域，仓库尚未覆盖：

```
□ 中文字体：微软雅黑/方正系列/汉仪字库对"商用嵌入"需授权
    小程序里用 CSS font-family 指定系统字体 ≠ 侵权；
    把字体文件转 webfont 打包进小程序 = 需授权（高风险动作）
    安全做法：开源可商用字体（思源黑体/宋体、阿里普惠体等，仍需按其许可证核对）
□ 图标库：MIT 可直接用；CC-BY 需署名；Iconfont 上作者自定义许可逐个看
□ 插画/摄影：Freepik 等免费层需署名且禁止再分发；AI 生成素材留存生成记录
□ 组件库：WeUI/Vant/TDesign 开源许可证各自核对商用条款（技术选型见 01）
□ 第三方音效/BGM：短视频与小程序内音频是重灾区
```

判断口诀：**"能不能商用"看许可证原文，不看网站按钮上的"免费下载"。**

## 6. 数据处理合规：同意、用户权利、AIGC 与跨境

### 6.1 开发者最小化原则

```bash
# 最小化原则的四项要求：
# - 目的限制：只为声明目的处理
# - 明示告知：处理前明确说明
# - 逐项授权：不捆绑、不默认
# - 默认关闭：非必要功能默认不采集
```

> 来源：`../legal/data-compliance-guide.md:63-68`

### 6.2 同意的四种类型

```bash
# 同意类型 | 适用场景 | 技术要求
# 明示同意 | 一般个人信息处理       | 主动勾选，不得默认勾选
# 单独同意 | 敏感信息、跨境传输、
#            公开披露               | 独立弹窗，不可捆绑
# 书面同意 | 向第三方提供个人信息   | 电子签名或纸质确认
# 撤回同意 | 用户随时可撤回         | 提供便捷的撤回入口
```

**【专题补写】** "书面同意：向第三方提供个人信息"这一行对 OPC 特别容易忽略：把用户数据同步给第三方 SaaS、CRM、客服系统、分析平台，都算向第三方提供。判定标准是你有没有在隐私政策的"信息共享"段落里**列出该接收方**（模板第 3 段，见第 7 节）。

> 来源：`../legal/data-compliance-guide.md:70-77`

**【专题补写】** 落到小程序代码上的唯一入口是隐私授权流程（`wx.requirePrivacyAuthorize` / `__usePrivacyCheck__` 等技术实现在 [02-development.md](./02-development.md)）。法规侧的判定标准是：**用户没读过的同意不是同意，一次勾选换五项授权是捆绑授权**。

### 6.3 安全措施与跨境

```bash
# 技术措施：
# - 传输加密：全链路 TLS 1.3，禁止明文传输个人信息
# - 存储加密：敏感字段 AES-256，密钥与数据分离管理
# - 脱敏展示：手机号中间四位、身份证中间八位掩码
# - 访问控制：基于角色的最小权限，操作留痕
# - 数据生命周期：明确保留期限，到期自动删除或匿名化

# 跨境四问（开发者涉及出境时需确认）：
# 1. 是否触发安全评估（100 万人以上个人信息，或 10 万人以上敏感信息）
# 2. 是否已签署标准合同并在网信办备案
# 3. 是否获得用户单独同意
# 4. 接收方所在国家/地区的数据保护水平

# 跨境三机制：
# - 安全评估：45-60 个工作日
# - 标准合同：15 个工作日备案
# - 个人信息保护认证
# 自贸区负面清单可放宽部分场景
```

> 来源：`../legal/data-compliance-guide.md:79-94,161-174`

**【专题补写】** 对 OPC 的现实含义：**把后端放在境外（Vercel/Supabase/Firebase/Cloudflare Workers）+ 收集国内用户个人信息，本身就构成跨境提供**。这不是"性能慢一点"的问题，而是合规义务问题。多数个人/个体户小程序不具备走安全评估或标准合同备案的能力，因此：**只要涉及个人信息，后端选境内且已完成 ICP 备案的服务器**（技术侧的域名白名单约束见 [02-development.md](./02-development.md)；这一条也与 05 里"境外 MVP 栈对国内小程序不成立"的结论互为因果）。

### 6.4 AIGC 相关义务

```bash
# 若小程序含生成式 AI：
# - 算法备案
# - 训练数据合法性
# - AI 生成内容标识
# - 深度合成相关规定
# - 安全评估
```

> 来源：`../legal/data-compliance-guide.md:178-192`

**AI 生成内容的著作权归属与标识义务**（原文在知识产权册，与上面的合规清单是同一件事的两面：一面决定"你生成的东西归不归你"，一面决定"你必须怎么标"）：

```markdown
### 7.1 AI作品著作权归属
- **现行规则**：北京互联网法院(2023)判例认定，人类对AI生成内容做出实质性智力贡献时，可享有著作权
- **关键因素**：提示词设计的独创性、参数调整的创造性、后期编辑的程度
- **企业建议**：保留AI创作过程记录（提示词、迭代版本），证明人类智力投入

### 7.2 AI训练数据版权争议
- **合理使用抗辩**：目前中国法律未明确AI训练是否构成合理使用
- **风险防控**：使用授权数据集、公开许可数据、自有数据训练
- **行业趋势**：部分平台已推出AI训练授权许可机制
- **合规建议**：建立训练数据来源台账，标注授权依据

### 7.3 AIGC标识义务
- AI生成的文本、图片、音频、视频需添加显著标识
- 深度合成内容（换脸、配音）需双重标识（显著+隐式水印）
- 服务提供者应在用户协议中明确标识义务
- 违反标识义务可被处以警告、罚款、暂停服务
```

> 来源：`../legal/ip-protection-guide.md:204-222`

**【专题补写】** 三条给 OPC 的落地动作，按成本从低到高：

1. **标识做进渲染层，不做成开关**。生成结果输出时就带水印或"AI 生成"文案，而不是让用户勾选。开关一旦被关掉，义务就落在你身上；写死在渲染层，责任边界清楚。深度合成（换脸、克隆声音）在此基础上再加隐式水印——**这类功能对个人主体的小程序建议直接不做**，仓库尚未覆盖其准入门槛，风险远大于收益。
2. **提示词与迭代版本进 Git**。理由不是"方便复用"，而是原文判例口径里"实质性智力贡献"要靠过程记录证明。一旦有人抄你的 AI 生成素材，或者你被别人抄，这份记录是唯一的低成本证据。做法：把生成配置写成仓库里的 `.json`/`.md` 文件提交，而不是留在对话记录里。
3. **训练/微调前先确认数据来源**。多数 OPC 不做训练，但会做"用用户数据优化体验"。原文口径是"未明确构成合理使用"，也就是说这是**尚未有定论的争议区**，不是"法无禁止即可为"。保守做法：用户数据默认只用于该用户自己的体验，跨用户用于模型改进需要单独同意（回到 §6.2 的"单独同意"），并在隐私政策里写明。

> 政策快照｜截至 2026 年 10 月。AIGC 标识与深度合成的具体规则以国家网信办等发布的现行规定及其配套标准为准，这一领域调整频繁，上线前须核对原文。

### 6.5 用户七项权利，落到产品里是七个入口

原文的权利清单是员工视角（"你可以怎么行使"）。**在小程序里，每一行的"行使方式"列就是你的开发任务清单**：那一列写的功能你必须真的做出来，否则权利无法行使，隐私政策写了也构成不实陈述。

| 权利类型 | 具体内容 | 行使方式 |
|----------|----------|----------|
| **知情权** | 了解数据被谁收集、如何使用 | 查阅隐私政策、向DPO询问 |
| **决定权** | 同意或拒绝数据处理 | 勾选/取消授权 |
| **查阅复制权** | 查看自己的数据副本 | App内"个人信息查阅"功能 |
| **更正补充权** | 修改不准确的信息 | 账户设置中修改 |
| **删除权** | 要求删除个人信息 | 注销账户或专项申请 |
| **可携带权** | 将数据转移至其他平台 | 申请数据导出 |
| **拒绝自动化决策** | 拒绝算法推荐/画像 | 关闭个性化推荐 |

> 来源：`../legal/data-compliance-guide.md:99-110`

**【专题补写】** 按"能不能在小程序里做"拆成三档，别一次全做：

| 档 | 权利 | 小程序侧做法 | 成本 |
|---|---|---|---|
| **平台已给，只需接** | 知情权、决定权 | 隐私政策页 + 隐私接口授权弹窗（代码见 [02-development.md](./02-development.md)）。微信侧的授权状态本身可在后台查询与撤回 | 低 |
| **必须自己写** | 查阅复制权、更正补充权、**删除权** | "我的"页里三个入口：数据查阅、资料编辑、**注销账号** | 中 |
| **可以只留邮箱** | 可携带权、拒绝自动化决策 | 政策里写明"通过联系客服申请"，人工在若干工作日内处理；无算法推荐则不需要第三个 | 低 |

两个最容易漏的：

- **注销入口**。删除权在国内 App 治理里是被通报的高频项，而小程序后台**没有**平台级的"注销账号"能力，必须自己实现。最小实现：软删除 + 到期硬删除（并写清保留期限，见 §7.1），比"不做"成本低一个数量级。
- **撤回同意后真的停止收集**。原文只写"勾选/取消授权"，工程上的坑是：用户取消后代码仍在上报。做法是在埋点入口统一判断授权状态，而不是每个调用点各自判断（埋点侧的对应设计见 [03-operations.md](./03-operations.md)）。

> 政策快照｜截至 2026 年 10 月。微信等平台提供的授权管理与撤回能力会调整，具体接口与后台入口以当期官方文档为准。

### 6.6 一个人的合规自查：可以用哪些公共渠道和标准

原文的工具表按企业采购视角写，对 OPC 多数不可用；但**同一节的"查询渠道"是可以直接用的免费自查入口**，其中两条对个人尤其有价值。

| 工具类型 | 推荐方案 | 用途 |
|----------|----------|------|
| **同意管理平台(CMP)** | OneTrust、秒针合规 | 管理用户授权和撤回 |
| **数据地图** | BigID、Collibra | 可视化数据流转路径 |
| **隐私影响评估** | 自建模板+律所审核 | PIA评估流程化 |
| **合规审计** | 四大/专业律所 | 年度合规审计 |
| **SDK检测** | 工信部检测平台 | App嵌入SDK合规检查 |

```markdown
- 国家网信办官网：政策法规、执法动态
- 工信部App治理通报：每月违规App名单
- 全国信息安全标准化技术委员会：国家标准（GB/T 35273等）
- 中国信通院：行业白皮书和合规指引
```

> 来源：`../legal/data-compliance-guide.md:230-245`

**【专题补写】** 上面企业向的工具表里，对 OPC 真正可用的只有三件：**工信部 SDK 检测平台**（免费，自查嵌入组件是否超范围收集）、**每月违规通报名单**（看同功能产品因为哪一条被点名，比读法条快得多）、**GB/T 35273**（《个人信息安全规范》，把法条翻译成可勾选项的 checklist，写隐私政策时按它的附录逐项对照）。OneTrust/BigID/年度审计这一类可以直接跳过——不是"以后再说"，而是**规模不到、不适用**。

关于"要不要做"，原文 FAQ 给了明确答案：

```markdown
**Q: 小型创业公司也需要做数据合规吗？**
A: 是的。PIPL适用于所有处理个人信息的组织，不论规模。但合规要求可根据数据处理量适当简化，核心是做好隐私政策、用户同意和数据安全基本措施。

**Q: 使用第三方SDK需要注意什么？**
A: 需在隐私政策中披露所有SDK名称、收集数据类型和目的；确保SDK已获用户同意；定期检测SDK是否存在超范围收集行为。
```

> 来源：`../legal/data-compliance-guide.md:251-255`

**【专题补写】** "不论规模"加上"可适当简化"这两句合起来读，实操结论是：**义务不打折，形式可以省**。对一个人的小程序，"适当简化"后的最小合规集是四件——隐私政策页（八要素齐，见 §7.1）、授权前不采集（§6.2）、境内已备案后端（§6.3）、SDK 披露与定期自查（本节）。第 1 节的上线前清单已把这四件排进流程。

### 6.7 处罚量级（为什么这不是"注意事项"而是"上线门槛"）

```bash
# 既有处罚案例：
# - 某短视频 App（2023）：100 万元，未经同意收集未成年人信息
# - 某电商平台（2024）：500 万元，大数据杀熟、自动化决策不透明
# - 某金融 App（2024）：200 万元，强制授权、超范围收集征信数据

# 企业启示：
# - 处罚金额与营收挂钩（PIPL 最高可达年营业额 5%）
# - 直接责任人可被处以 10 万 - 100 万元罚款
# - 严重违法可吊销营业执照、禁止从业
```

> 来源：`../legal/data-compliance-guide.md:205-212`

**【专题补写】** "直接责任人"这一条对 OPC 是**结构性风险**：公司只有你一个人，你同时是法定代表人、信息安全负责人和开发者。罚款上限对个人不是 10 万这个数字，而是"这一笔就够让公司结束"。因此把"逐项授权、默认关闭、撤回入口"当功能做进产品，而不是当文档写在政策里。

## 7. 隐私政策文本：八段模板与两处坑

### 7.1 两段要素清单需要合并

PIPL 口径要求（法规侧，缺项即不合规）：

```bash
# 一份合规的隐私政策应包含：
# 1. 数据控制者信息及联系方式
# 2. 收集的个人信息类型及目的
# 3. 数据保留期限
# 4. 数据共享和披露对象
# 5. 用户权利及行使方式
# 6. 跨境传输说明
# 7. 未成年人保护条款
# 8. 政策更新通知机制
```

> 来源：`../legal/data-compliance-guide.md:218-229`

仓库现成的模板（Apple 上架口径，八段结构）：

```markdown
# 隐私政策
## 1. 信息收集   （个人身份信息 / 设备信息 / 使用数据 / 位置信息）
## 2. 信息使用   （提供和改进服务 / 个性化 / 推送 / 分析趋势）
## 3. 信息共享   （不与第三方广告商共享 / 法律要求时披露 / 服务提供商）
## 4. 数据安全   （加密存储 / 安全传输协议 / 访问控制机制）
## 5. 用户权利   （访问 / 更正 / 删除账户及数据 / 导出）
## 6. 儿童隐私   （不收集 13 岁以下儿童信息 / 发现即删除）
## 7. 政策更新
## 8. 联系我们
```

> 来源：`../super-individual/app-publishing-guide/ios/privacy-policy.md:31-79`

**【专题补写】** 两份清单**不是一份**。直接套 Apple 模板会在国内留下三个缺口：

| PIPL 要求 | Apple 模板 | 处置 |
|---|---|---|
| 数据保留期限 | **无** | 必须补一段，写清各类数据保留多久、到期如何删除 |
| 跨境传输说明 | **无** | 后端在境外必须写；后端在境内也应写明"不跨境" |
| 未成年人保护 | 写的是"13 岁以下不收集" | 国内口径是**不满 14 周岁需监护人同意**，见下 |

### 7.2 坑一：13 岁 vs 14 岁

```bash
# 教育/未成年人场景：不满 14 周岁的个人信息处理需取得监护人同意；
# 不得向商业机构提供学生信息；不得强制采集人脸、声纹
```

> 来源：`../legal/data-compliance-guide.md:143-148`

**【专题补写】** Apple 模板里的"不收集 13 岁以下儿童信息"来自 COPPA，是国内政策里"不收集"的保守写法。国内法定门槛是**不满 14 周岁需监护人同意**——即"可以收集，但要家长同意"。两者不冲突，但**不能只抄 13 岁那句就交差**。最省事的合规结构：产品明确定位为成年人使用，并在隐私政策里写"不面向未成年人提供服务，不主动收集未成年人个人信息"，同时在设计上不出现儿童定向内容。

### 7.3 坑二：托管方案对国内小程序不可用

原文推荐的五种隐私政策托管：GitHub Pages（免费、推荐）、Vercel（推荐、简单）、Netlify、Notion、第三方生成器。

> 来源：`../super-individual/app-publishing-guide/ios/privacy-policy.md:81-262`

**【专题补写】** 这五种是给 **iOS App** 写的（App Store Connect 需要一个可访问的 URL）。小程序场景不同：

- 小程序的隐私政策主要在**微信公众平台后台配置**，并在小程序内提供入口页（技术实现见 [02-development.md](./02-development.md)）。
- GitHub Pages / Vercel / Netlify 的域名**无法完成 ICP 备案**，不能作为小程序**业务域名**使用；Notion 页面同理且不稳定。
- 结论：**隐私政策用小程序内的一个页面承载**（自己的已备案域名，或云开发静态托管），另备一份公网可访问文本用于对外展示与主体审查。上面五种托管方案对国内小程序只可作"对外展示位"，且优先自托管在备案域名下。

### 7.4 页面可达性与分类要点

```bash
# 技术要求：必须 HTTPS / 页面可正常访问 / 不能有访问限制（如登录）
#          / 内容必须完整，不能是 placeholder

# 合规检查：
# □ 页面可正常访问（HTTPS）
# □ 内容完整，不是 placeholder
# □ 说明所有数据收集类型
# □ 说明数据使用目的
# □ 说明第三方 SDK
# □ 提供联系方式
# □ 包含儿童隐私条款（如适用）
# □ 定期更新并标注日期

# 按类型补重点：
# 工具类：数据最小化 / 是否本地存储 / 是否上传 / 第三方 SDK 说明
# 社交类：UGC 处理 / 公开信息范围 / 屏蔽举报机制 / 好友关系数据
# 电商类：支付信息安全 / 订单数据存储 / 配送信息 / 退换货数据
```

> 来源：`../super-individual/app-publishing-guide/ios/privacy-policy.md:19-27,337-378,407-418`

**【专题补写】** 第三方 SDK 说明这一项在小程序里同样适用，且**必须与实际使用的接口权限一致**。原文的 SDK 清单（Firebase/Google Ads/Facebook/Adjust/AppsFlyer）在小程序里基本都用不了，要替换为实际使用方：**流量主广告组件、微信开放接口的数据字段、自建分析后端、云开发**。写法沿用原文模板结构（服务名 / 用途 / 数据类型）。

两个生成工具的操作路径与报价：

仓库自带的静态页面模板（含样式，直接可发布）：

**【专题补写】** 三份素材放在一起看，结论是**都能用，但都不能直接用**。逐条对照 §7.1 的 PIPL 八要素，上面这份 HTML 的缺口是明确的：

| PIPL 八要素 | 这份模板 | 需要补什么 |
|---|---|---|
| 数据控制者信息及联系方式 | 只有 `support@example.com` | 补**主体名称**（个体工商户执照全称）与主体类型 |
| 收集类型及目的 | 有，但泛化 | 按小程序实际调用的接口逐条列（授权代码在 [02-development.md](./02-development.md)） |
| **数据保留期限** | **无** | 补一段：各类数据存多久、注销后多久删除 |
| 共享与披露对象 | 只写"不共享" | 有流量主、云开发、第三方 SDK 时，"不共享"就是不实陈述，必须改 |
| 用户权利及行使方式 | 只写"联系我们" | 与 §6.5 对齐：能自助的写入口，不能自助的写处理时限 |
| **跨境传输说明** | **无** | 后端在境内也要写明"不跨境" |
| **未成年人保护** | **无**（模板没有，Apple 版有但写 13 岁） | 按 §7.2 的国内口径写 |
| **政策更新通知机制** | 只有"更新日期" | 补：变更如何告知（站内弹窗/公告），重大变更重新取得同意 |

生成工具同理：iubenda 与 Termly 的向导问的是 GDPR / CCPA 口径（是否追踪、第三方 Cookie、Do Not Sell），**不会问你数据保留期限和 14 周岁**。可用法是把它当"防漏清单"，生成后按上表逐段改写；**不要用它给的独立 URL**——那是境外域名，与 §7.3 的结论冲突，不能作为小程序业务域名。

落地建议（成本从低到高）：

```
① 小程序内一个页面承载隐私政策（自己的已备案域名，或云开发静态托管）
② 模板从上面这份 HTML 起手，按表格补齐 5 个"无"
③ 更新日期改为实际发布日，并在页面底部留版本号（如 v1.0 / 2026-10）
④ 另存一份纯文本放仓库，改一次 commit 一次——审查时能证明"何时告知了什么"
```

第 ④ 条容易被跳过，但它是 §6.5 里"知情权"的证据来源：政策改版前后的差异，只有进版本库才说得清。

> 政策快照｜截至 2026 年 10 月。iubenda 报价与免费层限制会变，付费前以官网当期价格为准。

### 7.6 用户协议：小程序场景为什么反而更需要

原文把用户协议（Terms of Service）列为"部分平台要求必须提供 / App Store 审核可能要求"，并给了七节骨架：

```bash
# 用户协议（Terms of Service）的用途：
# 1. 明确用户和开发者的权利义务
# 2. 避免法律纠纷
# 3. 部分平台要求必须提供
# 4. App Store 审核可能要求
```

```markdown
#### 1. 接受条款      使用本 App 即表示您同意本协议。
#### 2. 服务描述      写明小程序名称与一句话功能描述
#### 3. 用户账户      信息真实 / 账户安全自负 / 有权暂停违规账户
#### 4. 知识产权      App 内内容归我们所有 / 未经授权不得复制
#### 5. 免责声明      服务按"现状"提供 / 不对服务中断负责
#### 6. 终止条款      用户可随时停止使用 / 我们可终止服务
#### 7. 联系我们      Email
```

> 来源：`../super-individual/app-publishing-guide/toolchain/assets.md:282-327`；原文模板中两处方括号变量已按上下文改写为说明性文字

**【专题补写】** 小程序平台不强制你交用户协议，所以这一页**大概率是空的**——而它恰好是事后举证最容易的一环。三个具体的用途，对应三处必须补写的条款：

| 场景 | 只有隐私政策时会怎样 | 用户协议里要写的那一句 |
|---|---|---|
| **用户发违规内容被平台处罚** | 你封他号，他投诉你"无故停止服务"，微信侧看的是你有没有事先约定 | "违反法律法规或平台规范的账号，我们有权限制或终止服务"（骨架第 3、6 节扩写） |
| **UGC 内容被搬运、被侵权** | 骨架第 4 节写"App 内内容归我们所有"——**用户生产的内容这句话并不成立** | 改为"用户对其上传内容保留权利，并授予我们在本服务内展示、分发的非独占许可" |
| **含 AI 生成内容** | §6.4 的标识义务无处承接，原文写的"服务提供者应在**用户协议**中明确标识义务"正是这一页 | "本服务的部分内容由 AI 生成，已按法规添加标识，不构成专业建议" |

至于 AIGC 那条，与第 11 节的预付费、第 8 节的特殊行业不冲突：涉及医疗、金融、教育的结论性输出，免责声明并不能替代资质（见 §8）。

生成工具与报价沿用 §7.5，ToS 侧原文给的入口：

```bash
# Termly（免费）：
# https://termly.io/generator/terms-and-conditions-generator/

# iubenda（付费但全面）：
# https://www.iubenda.com/
```

> 来源：`../super-individual/app-publishing-guide/toolchain/assets.md:329-337`

**【专题补写】** 这类生成器产出的条款以美国加州法与 GDPR 为默认口径，管辖、争议解决、消费者撤回权等在国内另有一套规则。**用它的骨架，不用它的条文**：至少把管辖法院改为你所在地、把"随时无理由终止"改成与第 11 节预付费退还规则一致的表述。另有一条最容易忽略的一致性要求：用户协议与隐私政策里的**主体名称和联系方式必须完全一致**，两份文件写成不同主体是国内小程序常见的低级不合规。

## 9. 平台运营规范与违规处罚

**【专题补写】** 本篇最大空白：三端平台运营规范与违规处置的**具体条款、处罚分级、金额**，仓库零覆盖。因此本节只写**结构、分类和自检办法**，所有数字进"需你复核的事实"表，一律以各端官方《运营规范》原文为准。

### 9.1 三种后果，不是一个"下架"

```
平台侧（三端通用结构）：
  轻度  警告 / 要求整改 / 限制功能（如限制分享、限制搜索露出）
  中度  版本回退 / 单品下架 / 限制新增用户 / 清退活动
  重度  封禁接口 / 封禁账号或主体 / 支付资金冻结 / 保证金扣除
法定侧：
  市场监管（虚假宣传、消费者权益、价格）→ 罚款、责令改正
  网信/工信（个人信息、内容）→ 本篇 6.5 的量级
  民事（权利人投诉：名称侵权、素材侵权、代码抄袭）→ 平台处置 + 索赔
```

**"支付资金冻结"对 OPC 是致命的**：现金流结构见 [05-monetization.md](./05-monetization.md)——账户余额即运营资金，冻结等于断流。这是为什么变现动作前要先过红线检查。

### 9.2 诱导分享红线清单

05 的活动裂变、04 的分享玩法都指向这张表。**"分享后才能继续"是绝大多数触雷动作**：

```
高危（明确违规方向，几乎必被处置）：
□ 强制分享：不分享就不能使用/不能看结果/不能领取
□ 利益诱导分享：分享得现金、得积分、得抽奖资格
□ 分享话术含夸大或胁迫（"不转不是中国人"式、"已被封"式伪告警）
□ 诱导好友助力解锁个人权益，且助力方本身无实际收益

相对安全（仍需在平台规范内）：
☑ 用户主动分享，分享本身不解锁权益
☑ 分享内容指向真实价值（成果页、榜单、作品），而非奖励
☑ 奖励发放对象为"使用行为"而非"分享行为"
☑ 邀请/推荐机制在平台明确允许的类目与工具范围内
```

> **【专题补写】** 红线分类为编排补写。做活动前逐条对照，判据不是"别人也在做"，而是**各端运营规范原文**（05 已给出同一约束：分销层级判断亦以原文为准，见下）。

### 9.3 虚假宣传与绝对化措辞

```
名称/简介禁用与高风险措辞：
□ 绝对化用语："最""第一""国家级""全网最低"
□ 身份误导："官方""旗舰""腾讯/微信合作"（无授权即侵权）
□ 疗效与收益承诺：医疗效果、金融收益保证、"稳赚""包过"
□ 与实际功能不符：类目外功能描述（与第 3 节联动）
□ 刷单与虚假评价：评价数据造假同时触发电商侧义务（第 11 节）
```

提审阶段的处置（如何改、如何复提）归 [02-development.md](./02-development.md)；本节关注**已上线后被识别**的后果，二者互链不重复。

# 多级分销（三层及以上）+ 拉人头触碰红线。

### 9.6 广告标注与内容合规：为小程序引流的每一条内容都算

```markdown
- **广告标注**：商业合作内容需标注"广告""推广"等字样
- **著作权**：引用他人内容需注明出处，图片注意版权
- **信息安全**：不得泄露个人隐私和商业机密
- **言论边界**：避免虚假信息、恶意诋毁、煽动对立
```

> 来源：`../super-individual/self-media-guide.md:360-365`

**【专题补写】** 这四条写在自媒体册里，但**小程序是它们的下游**：你为小程序做的每一条视频号、公众号推文、抖音短视频、朋友圈投放素材，都落在这四条的射程内。逐条对应到实操：

| 原文条款 | 在小程序引流场景下的具体形态 | 风险等级 |
|---|---|---|
| 广告标注 | 品牌方付费让你在内容里挂它的小程序/组件；**接商单的内容必须显式标注**，藏在文案中间不算 | 高（可被平台限流并记分，对应 §9.1 的分级处置） |
| 广告标注 | 自己小程序的流量主广告位由平台投放并自带标识，**不需要**你逐条标注；但你自己写的"限时优惠""点击领取"落地页文案要符合 §9.3 措辞红线 | 中 |
| 著作权 | 分享卡片配图、引导视频里的 BGM、截图里出现的他人 UI——**素材来源要与小程序内一致地授权**（字体与素材见 §5.4） | 高（分享图是平台可查的固定资产） |
| 信息安全 | 用真实用户案例做推广：聊天截图、订单金额、昵称头像都属个人信息，**必须打码或取得书面授权** | 高（直接触 §6 的 PIPL 义务） |
| 言论边界 | "帮你的小程序上首页""稳定日入 XXX"这类获客话术，同时触 §9.3 虚假宣传与 §9.2 诱导分享 | 高 |

第 3 行是 OPC 最容易踩的一条：内容号做推广时习惯性截一张"用户反馈"，而这张截图进了小程序的固定页面，就成了公开可查的个人信息处理行为。做法与 §6.2 一致——**要展示就换成正向反馈的抽象描述，或让用户在你的表单里勾选公开授权**。

内容侧的投放与运营动作（哪条内容挂哪个入口、投放素材怎么排）见 [04-growth.md](./04-growth.md)；本节只管"写了什么会被罚"。

## 10. 合同与接单风险

外包做小程序是 OPC 常见收入来源，合同条款是唯一防线。

### 10.1 必备合同条款（七组）

```
自由职业合同核心条款：

1. 合作双方信息
├── 委托方（甲方）信息
├── 受托方（乙方）信息
└── 双方联系方式

2. 项目范围与交付
├── 详细工作内容描述
├── 交付物清单和验收标准
├── 交付时间节点
└── 需求变更处理流程

3. 费用与支付
├── 项目总费用
├── 付款节点和比例
├── 付款方式和期限
├── 发票开具要求
└── 逾期付款违约金

4. 知识产权
├── 成果归属约定
├── 第三方知识产权声明
├── 乙方是否有展示权
└── 开源组件使用约定

5. 保密条款
├── 保密信息范围
├── 保密期限
└── 违约责任

6. 违约与终止
├── 双方违约情形
├── 合同解除条件
├── 违约金计算方式
└── 争议解决方式

7. 其他条款
├── 不可抗力
├── 法律适用和管辖
├── 合同生效条件
└── 附件清单
```

> 来源：`../super-individual/freelancing-guide.md:242-287`

**【专题补写】** 小程序外包项目在第 2、3、4 组上有三个专属坑：

```
第 2 组补：把"上线"定义为验收节点，并写明审核周期不由乙方控制
    审核周期原文为 3-7 天、首次可能更长（wechat.md:330）；
    备案 1-2 个月（第 2 节）。验收条款若不写"审核结果归甲方风险"，
    平台拒审会变成你的违约责任。

第 3 组补：资质与账号费用归属写清
    认证费、类目资质、软著、备案由谁办、谁出钱（费用口径见 05）。
    微信/支付宝/抖音的**账号与商户号必须归甲方持有**，
    写进交付清单——否则尾款争议时你手里捏着甲方资产，双方都难受。

第 4 组补："展示权"要具体到能否截图进案例集
    含"开源组件使用约定"这一条别省：甲方日后被 GPL/AGPL 追责，
    约定不清就是由乙方（你）承担。
```

**另一份合同骨架：内容合作八要素**（来自自媒体册，与上面的七组不是一套东西——七组是"你接开发单"，八要素是"你卖内容位/接推广单"，也就是 §9.6 那类商单）：

```
商业合作合同关键条款：
├── 合作内容：具体交付物和标准
├── 发布时间：明确的发布日期和时间
├── 修改次数：免费修改次数上限
├── 付款条件：预付款比例和尾款时间
├── 知识产权：内容版权归谁
├── 竞业限制：是否限制发布竞品内容
├── 违约责任：双方违约的赔偿方式
└── 争议解决：仲裁或诉讼管辖
```

> 来源：`../super-individual/self-media-guide.md:374-386`

**【专题补写】** 两份骨架并排看，八要素里有三条是七组**没有**的，而且正是接单时最容易口头答应的那三条：

| 八要素独有项 | 为什么七组里缺它 | 小程序场景怎么写 |
|---|---|---|
| **发布时间** | 七组只写"交付时间节点"，交付 ≠ 发布 | 写"交付并通过验收后 N 个工作日内发布"，并把平台审核周期排除在外（同 §10.1 第 2 组补） |
| **修改次数** | 七组用"需求变更处理流程"覆盖开发，不覆盖内容 | 明确"免费修改 X 次，超出按 Y 元/次"；这一条是内容类收入的主要利润守门员 |
| **竞业限制** | 七组完全没有 | **看清是"限制你发竞品内容"还是"限制你做竞品产品"**。前者是商单常规条款；后者若写成 2 年内不得开发同类小程序，已经接近竞业协议，个人主体签之前要评估（在职场景见 §10.3 与 [../legal/compete-agreement.md](../legal/compete-agreement.md)） |

反过来，七组里有三条是八要素**没有**的，接内容单时也必须补：**保密条款**（甲方品牌未公开的活动信息）、**不可抗力**（平台封禁/审核延迟导致无法发布，谁承担）、**成果归属与展示权**（能否把这条商单放进你的案例集）。

一句实操结论：**八要素当议程清单用，七组当合同正文用**。谈单时按八要素逐条问，落笔时用七组结构写，两套各自缺失的部分按上面两张表互补。

### 10.2 风险防范清单

```bash
# 风险 → 表现 → 防范措施
# 需求蔓延   | 客户不断增加新需求       | 明确范围、变更收费
# 拖欠付款   | 客户延迟或拒绝付款       | 分期付款、预付款机制
# 需求不清   | 双方对需求理解不一致     | 详细需求文档、原型确认
# 中途取消   | 项目进行中被取消         | 取消违约金条款
# 知识产权纠纷| 成果归属争议            | 合同明确约定
# 口头承诺   | 未落实到书面             | 所有沟通以书面确认
```

> 来源：`../super-individual/freelancing-guide.md:289-298`

### 10.3 在职做小程序的合规检查

```
在职做副业合规检查：

法律层面：
├── □ 检查劳动合同中的竞业限制条款
├── □ 检查保密协议的范围
├── □ 确认公司是否有禁止兼职的规定

```

**【专题补写】** 小程序场景下"使用公司资源"的边界要额外看清：**用公司邮箱注册小程序账号、用公司域名做业务域名、把小程序挂在公司云账号下**，三项都属"使用公司资源"，且都会在离职时变成权属争议。注册主体从第一天就用个人/自有个体户信息。

## 11. 电商法与预付费

**【专题补写】** 仓库对"电子商务经营者"身份义务与预付式消费**零覆盖**，本节只给结构与自查问题，具体条文以《电子商务法》《消费者权益保护法》及市场监管部门现行规定为准。

### 11.1 只要你开始卖东西，你就是电商经营者

```
身份判定：
  小程序内自营销售（实物/服务/虚拟商品）→ 电子商务经营者
  通过抖音小店等 A 平台销售 → 平台内经营者，义务部分由平台承接
  （A 平台 vs 自建商城的判据见 05「交易型变现」节）

义务清单（自查问句形式）：
□ 主体信息是否在小程序内显著公示？（名称、经营资质、联系方式）
□ 商品与服务信息是否真实、全面？（不得虚假或引人误解的宣传 → 与 9.3 同源）
□ 是否出具发票或购物凭证？（开票链路见 07-tax.md）
□ 是否适用七日无理由退货？（不适用类目须显著说明理由）
□ 订单数据与交易信息是否按规定留存？
□ 评价机制是否不得删除、不得篡改？
□ 自动定价/个性化推荐是否提供"不针对个人特征"的选项？
    （大数据杀熟、自动化决策不透明 → 6.5 处罚案例中 500 万元那条即此项）
□ 是否明确押金退还的方式与程序？（设押金须公示退还规则）
```

### 11.2 预付费：小程序最常见的投诉来源

```
适用形态：会员卡、次卡、储值卡、季/年费订阅、预售课程、包月社群

自查：
□ 预付金额、兑付方式、退还规则、有效期是否在支付前显著展示
□ 是否给退款出口（闭店/服务变更时的退还安排）
□ 是否保留单张凭证可核查的记录（避免"卷款"定性升级为刑事风险）
□ 服务未履约时是否主动通知并退款，而非等投诉
□ 高单价预售是否控制预收规模，不把预收款当利润花
    （现金流口径见 05「成本与现金流」节：预收款是负债，不是收入）
```

> **【专题补写】** 本节为结构补写。预付式消费在地方层面已有专门规定，具体到所在城市/行业的限额与备案要求，仓库尚未覆盖，须向当地市场监管部门核实。
