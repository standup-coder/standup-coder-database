# 示例复盘：一次收敛良好的调试对话

> **声明：本文为教学用示例对话，非真实会话日志。** 展示[bug 报告模板](../prompts/bug-report.md)在实际对话中的样子，重点是"先确认假设、再动手改"的节奏。

## 对话节选

> **新人**：现象：提交表单后控制台报 `TypeError: Cannot read properties of undefined (reading 'id')`，表单卡在提交态。复现：填完 /settings/profile 表单点保存必现。期望：保存成功并提示。环境：main 分支 `4f2a1c0`。已排除：接口本身正常（curl 返回 200 且有数据）。约束：不要改后端接口。

**Agent**：报错发生在提交后的响应处理。先给两个假设：A) 响应结构变了，代码读的是旧字段；B) 表单组件把响应对象错误传递。我先查处理响应的代码再验证，5 分钟内给出证据。

**Agent**：找到了。`src/pages/Profile.tsx:82` 读 `response.data.user.id`，但接口实际返回 `{ profile: {...} }`（见 `src/api/profile.ts` 的类型定义）。证据：类型定义与调用点字段名不一致。建议改成 `response.data.profile.id`。

> **新人**：先别改。为什么类型定义是对的、调用点却编译通过了？

**Agent**：`request()` 的返回类型是 `any`（`src/lib/http.ts:17`），所以字段名错误不会在编译期暴露。这也是同类 bug 会再犯的根源。

> **新人**：那修两处：1) 调用点改用正确字段；2) 把 `request()` 的返回改成泛型，让调用点显式声明类型。先写一个失败的类型检查用例证明问题存在，再修。

**Agent**：（给出类型层面的复现 → 修复 → `tsc --noEmit` 通过的证据链）

## 复盘：这个对话里做对了什么

1. **结构化报告自带"已排除"**：接口正常这一条，让 agent 直接跳过网络层，第一轮就定位到前端。
2. **要求证据，不接受断言**："找到了"不够，`文件:行号` + 与类型定义的对照才是证据。
3. **追问"为什么会编译通过"**：把单次 bug 升级成根源修复（`any` → 泛型）。只改字段名，同类 bug 下周就会换个地方再出现。
4. **先复现后修复**：类型检查用例先失败后通过，证明修复真的命中了问题。

## 常见的错误走法

- "帮我修一下这个报错"——没有现象/复现/已排除，agent 只能逐层猜测，烧掉大量轮次。
- agent 说"找到了"就直接说"改吧"——没有证据链，改错方向的成本和改对是一样的。
- 满足于改掉报错那一行——根源（`any`）还在，bug 会回归。
