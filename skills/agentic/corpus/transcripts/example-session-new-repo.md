# 示例复盘：第一次探索陌生仓库的对话

> **声明：本文为教学用示例对话，非真实会话日志。** 展示的是[接手陌生仓库](../workflows/onboarding-a-new-repo.md)工作流中"结构地图"一步的典型对话形态：agent 自信地输出，新人用抽查发现一个编造点。

## 对话节选

> **新人**：通读这个仓库，给我一份结构说明：入口、主要模块、依赖方向。控制在 60 行内。

**Agent**：这是一个 Vite + React 项目。入口 `src/main.tsx` → `src/App.tsx` 路由分发到三个页面模块……数据层在 `src/api/`，由 `src/lib/http.ts` 统一封装，请求拦截器里做了 token 注入……

> **新人**：抽查一下：`src/lib/http.ts` 里的拦截器，token 是从哪里读的？

**Agent**：抱歉，我重新核对了 `src/lib/http.ts`，其中并没有请求拦截器，token 是在 `src/api/client.ts` 的 `request()` 里手动传入 headers 的。之前的描述不准确。

> **新人**：好。那把结构说明里不准确的几处都按真实文件核对后重发，每处标注"已核对 <文件路径>"。

**Agent**：（重发版本，三处标注修正）

## 复盘：这个对话里做对了什么

1. **先要地图，再抽查**——没有直接相信第一版输出。agent 的结构描述风格流畅、细节具体，**恰恰是流畅度让它显得可信**；唯一有效的验证是打开被引用的文件。
2. **抽查点选得具体**：不是"你确定吗？"，而是"token 从哪里读的？"——一个能用文件内容直接判真伪的问题。
3. **把个例修正升级为全面核对**：发现一处编造后，要求全部标注核对来源，而不是只改那一处。

## 常见的错误走法

- 拿到第一版结构说明就直接开工——后面对代码的每个判断都建立在这张（可能有错的）地图上。
- 问"你确定吗？"——agent 会回答"确定"，这不构成验证。
- 发现一处错误后只修一处——剩余的编造点会延后在更贵的环节暴露（比如改错文件）。
