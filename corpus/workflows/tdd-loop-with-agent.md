# 工作流：与 agent 协作 TDD 循环

让 agent 写代码最大的风险是"它说完成了，但验收标准没有被客观检验"。TDD 循环把这个风险变成流程：**每一步都有可运行的判据**。

## 循环（每个小功能走一圈）

### 1. 红：先写一个会失败的测试

> "为 <行为> 写一个失败测试。只写测试，不写实现。写完运行，把失败输出贴给我。"

**人工检查点**：确认失败原因是"功能不存在"，而不是测试本身的语法错误——后者会让你在错误的地方绕圈。

### 2. 绿：最小实现

> "用最小实现让这个测试通过。不许改动其他测试，不许顺手重构。"

坚持"最小"：agent 很喜欢一步到位写一堆"未来会用"的抽象，那是下一轮循环的事。

### 3. 重构：在绿灯保护下清理

> "测试全绿。现在做重构：<具体指出要清理什么，如提取重复逻辑/改名>。每步重构后跑测试，红了就回退该步。"

### 4. 回到 1

下一个行为，再走一圈。三个小循环好过一个大循环。

## 为什么不直接"写代码+写测试一起"

- 一起写时，agent 会照着实现写测试——测试断言的是"实现做了什么"而不是"应该做什么"，测试失去判据价值。
- 分开写，且**先红后绿**，你至少确认过：测试真的在测东西（红过），实现真的被测试约束（绿了）。

## 常见坑

- **让 agent 批量写 10 个测试再实现**：回到"测试跟着实现走"的老路。一次一个行为。
- **跳过人工检查点**：第 1 步的失败输出和第 2 步后的全量测试结果，都值得花 30 秒亲自看。
- **测试过拟合实现细节**（断言了内部调用顺序）：改实现就碎。要求 agent 断言**外部可观察行为**。
