# 小程序设计

OPC 做小程序，设计阶段最容易犯两个相反的错：一是拿 Web 产品的整套设计系统直接套，二是把小程序当成"简版网页"随便画。这两者都会让你在提审和首屏数据上付出代价。本篇解决三件事：**做之前怎么判断这个小程序值得做**、**画的时候小程序特有的视觉约束是什么**、**上线节奏怎么排**。

技术实现见 [02-development.md](./02-development.md)；设计要落到哪些指标上见 [03-operations.md](./03-operations.md)。

## 本篇结构

```
判断要不要做   → 小程序优势清单、需求验证五步法、形态适配检查、竞品分析、A 型失败模式、壁垒自查
怎么画         → rpx 与 750 基准、胶囊避让、安全区、包体限制、组件库选型
画成什么体验   → UX 五原则、首屏质量线、用户旅程、onboarding
素材从哪来     → 图标库、App 素材在仓库里的位置、分享图与头像尺寸
怎么推进       → 双周迭代 SOP（改写成提审节奏）、与 Web 设计系统的差异
```

## 1. 需求验证：这个小程序值不值得做

小程序相比 App 的最大优势是**验证成本低**——不用装机、不用应用商店审核周期、分享即达。所以它天然适合放在"需求验证"这一环，而不是"产品成熟后再补的渠道"。

仓库对小程序优势的原始记录，其中"开发成本低""审核周期短""依托大平台流量"三条正是"验证成本低"的三个构成：

```bash
# 相比原生 App：
- 无需安装
- 开发成本低
- 审核周期短
- 依托大平台流量
- 更新便捷

# 适合场景：
- 工具类服务
- 电商交易
- 内容阅读
- 线下连接
- 用户触达
```

> 来源：`../super-individual/app-publishing-guide/mini-program/README.md:21-33`

**【专题补写】** 下半张"适合场景"是**平台侧**的场景分类，回答"哪类业务在小程序里跑得通"；它不等于 OPC 的形态判断，后者要看成本与验证速度，见下文形态适配检查。两张清单叠在一起才构成完整的第一问。

```
Step 1：观察自己的痛点
├── 你每天工作中最烦的是什么？
├── 你重复做的低效事情是什么？
├── 你付钱买工具解决的是什么问题？
└── 原则：解决自己的痛点，100万人也有同样痛点

Step 2：验证他人也有同样痛点
├── 在Reddit/V2EX/即刻搜索相关问题
├── 看有多少人在抱怨同样的事
├── 查看竞品评论区的负面反馈
└── 目标：找到100+人在公开抱怨的痛点

Step 3：评估付费意愿
├── 在社群中问："如果有个工具能解决这个问题，你愿意付多少钱？"
├── 创建Landing Page收集邮箱
├── 目标：100+邮箱或10+预付款
└── 没有付费意愿的痛点 = 伪需求

Step 4：评估市场规模
├── TAM（总市场）：假设100%渗透率
├── SAM（可服务市场）：你能触达的
├── SOM（可获得市场）：第一年的目标
└── 公式：SOM = 目标用户数 × ARPU × 渗透率

Step 5：评估可行性
├── 技术可行性：你能做吗？AI能做吗？
├── 资源可行性：需要多少时间和金钱？
├── 竞争可行性：有巨头在做吗？你能差异化吗？
└── 决策矩阵：高需求 + 高付费意愿 + 高可行性 = 做
```

> 来源：`../super-individual/opc-product-design.md:77-105`

**【专题补写】** 在 Step 5 之后，小程序还需要多问一道"**这个需求适不适合小程序形态**"，因为不适配的情况做得再快也是白费：

```
小程序形态适配检查：

适合做小程序：
├── 低频但刚需（预约、报名、查物流、领票）
├── 有明确线下场景（扫码点单、门店核销、活动签到）
├── 依赖社交关系传播（拼团、助力、分享测试）
├── 单次使用时长 < 10 分钟
└── 用户不愿为此装一个 App

不适合做小程序（该做 App 或 Web）：
├── 高频重交互（专业工具、编辑器、长时间沉浸内容）
├── 依赖后台常驻、系统级推送、本地文件、蓝牙长连接
├── 需要复杂账号体系跨端同步（小程序登录态绑定在平台内）
├── 需要自主变现闭环（iOS 类场景的平台虚拟支付限制，见 05）
└── 强依赖非平台流量（SEO、外链导流，小程序不能被搜索引擎抓取）
```

> 政策快照｜截至 2026 年 10 月。平台规则会调整，发布前请核对官方文档，以官方为准。

**【专题补写】** 需求验证这一环在仓库里还有一个反面案例撑着。OPC 失败案例四型的归属划分是本篇的判断：A 型（技术自恋）是纯设计问题，落在本节；C 型的"壁垒"半句同样是产品问题，见本节末尾；B 型（平台依赖）是运营问题，见 [04-growth.md](./04-growth.md) 第 13 节；D 型（现金流）是收入结构问题，教训四条同样转录在 [04-growth.md](./04-growth.md) 第 13 节末尾，钱的节奏与储备口径见 [05-monetization.md](./05-monetization.md) 第 7 节。原文对 A 型的记录：

**失败模式A：技术自恋型**

```
典型案例：
├── 背景：大厂工程师，技术能力强
├── 产品：自研框架/工具
├── 问题：过度工程化，追求技术完美
├── 结果：开发6个月，用户不到100人
├── 原因：没有验证需求，闭门造车

教训：
├── "完成 > 完美"
├── 2周MVP法则必须遵守
├── 技术复杂度与商业价值不成正比
└── 用户反馈比代码质量更重要
```

> 来源：`../super-individual/opc-case-studies.md:290-305`

**【专题补写】** A 型在小程序语境下比在 App 语境下更容易发生，因为**门槛降低把"能做完"和"有人要"之间的距离拉长了**：三平台都有完善的组件库、云开发和现成模板，一个人两周内确实能做出一个功能完整的小程序，于是"做出来"很容易被当成"验证过"。三条可执行的约束：

```
防 A 型的具体动作（都在本节已有清单里，此处点名顺序）：
├── Step 3 的付费意愿验证必须在写第一行代码之前完成
│   —— 小程序开发太快，快到足以掩盖"没验证"这件事
├── "2周MVP法则"在小程序上要拆成"1周写完 + 1周等提审"
│   —— 原意仍是两周内做出 MVP（见仓库多处 MVP 口径），但小程序多了一段不可压缩的
│      审核排队：周期以 3-7 天为主且首次通常更长，还有被拒风险（口径与处置手册见 02）
└── 技术复杂度自查：用了分包、云函数、自建后端里的几项？
    一个只做单一刚需场景的验证版，通常一项都不需要
```

同类样本的量化数据（"发布前没有验证需求"占失败者特征 80%、"过度追求完美延迟发布"占 65%）见 [04-growth.md](./04-growth.md) 第 13.1 节，本节不重复记录——这两条正是 A 型在社群调研里的统计投影。

**【专题补写】** 小程序的竞品不用去第三方数据平台估流量，在平台内就能看到：微信搜一搜结果页会展示竞品的**近 30 天使用人数**（部分类目），支付宝/抖音小程序详情页同样有使用量或评价信息。把这一列填进上表"流量估算"，比 SimilarWeb 更贴近实际。此外竞品分析要多看一项：**它的类目与资质要求是什么**——这直接决定你能不能上（见 [06-legal.md](./06-legal.md)）。

> 政策快照｜截至 2026 年 10 月。平台规则会调整，发布前请核对官方文档，以官方为准。

**【专题补写】** 四类里的 C 型（AI 工具依赖）教训四条已转录在 [04-growth.md](./04-growth.md) 第 13 节，本节不重复，只取它的设计含义——**去掉模型之后这个小程序还剩什么**。这一问要插进 Step 3 的付费意愿验证里：向用户验证的应该是"没有 AI 也愿意为此付费的那部分"，而不是"演示效果让人惊艳"。那部分通常是四类之一，且要在设计阶段选定，不能等上线后补：

```
壁垒候选：
├── 数据积累：用户用得越久，结果越准，换竞品要重新积累
├── 用户关系：私域位与内容资产（打法见 04 第 8.2 节）
├── 独家内容或供给：版权、线下资源、只有你拿得到的数据源
└── 履约能力：线下服务、时效、售后——复制不了的部分

判定：
└── 四项都填不满，就是去掉模型什么都不剩
    —— 那不是产品，是一段提示词的壳
```

小程序形态还会放大这个风险：组件库、模板与云开发把复制成本压得比原生 App 更低，同类产品的同质化以周为单位发生。这也是本节把"付费意愿验证必须在写第一行代码之前完成"排在防 A 型动作第一条的原因——开发速度快本身不构成优势，只有验证过的需求才构成。

```
├── 工具：Figma + AI插件 / v0.dev
```

**【专题补写】** 上面这条流程是 Web/SaaS 向的，用在小程序上有三个必须改的地方：

```
小程序原型的三个额外约束：

1. 画布尺寸按 750 × 1624 建（不是 375）
   原因：小程序以 750rpx 为设计基准宽度，画 750 宽的稿

3. 高保真阶段就出"空状态"和"异常态"
```

## 3. 小程序视觉规范

**【专题补写】** 仓库尚未覆盖小程序视觉规范，本节为专题补写，是 P0 级内容——不懂这几条，设计稿会直接无法落地。

### 3.1 rpx 与设计稿基准

`rpx` 是小程序的响应式长度单位：**无论机型屏幕多宽，屏幕宽度恒等于 750rpx**。

```
换算关系：
1rpx = 屏幕宽度 / 750

常见机型：
| 机型 | 屏幕宽度(CSS px) | 1rpx 实际 | 750rpx |
|------|------------------|-----------|--------|
| iPhone SE | 320 | 0.427px | 320px |
| iPhone 6/7/8 | 375 | 0.5px | 375px |
| iPhone X/12/13/14 | 390-393 | ~0.52px | 390px |
| iPhone 14/15 Pro Max | 430 | 0.573px | 430px |
| 常见安卓 | 360-412 | 0.48-0.55px | 360-412px |

设计稿基准：750 × 1624（iPhone 6/7/8 尺寸等比放大 2 倍）
├── 画 750 宽的稿 → 稿上 1px = 代码里 1rpx，零换算
├── 画 375 宽的稿 → 稿上 1px = 代码里 2rpx
└── 字号是唯一例外：正文建议用 px 而非 rpx
    原因：rpx 会让小屏手机字号等比缩小到看不清，
    微信也提供了 `text-size-adjust`，正文用 px 更稳。
    推荐：标题用 rpx（跟随大屏放大），正文用 px（保持可读）
```

```css
/* 典型写法 */
.container {
  width: 750rpx;        /* 通栏 */
  padding: 0 24rpx;     /* 左右留白，约 12px on iPhone6 */
}
.title { font-size: 36rpx; }   /* 约 18px */
.body  { font-size: 14px; }    /* 正文固定，不随屏幕缩放 */
```

### 3.2 胶囊按钮与自定义导航栏

微信右上角的**胶囊按钮**（… 和 ⊙）是系统常驻控件，**任何小程序都不能遮挡、不能自定义、不能改变位置**。这是小程序视觉规范里最硬的一条，也是自研导航栏最容易出问题的地方。

```
获取胶囊真实位置（不要写死数字）：

const menu = wx.getMenuButtonBoundingClientRect()
const sys  = wx.getWindowInfo()

自定义导航栏总高度 = (menu.top - sys.statusBarHeight) * 2 + menu.height + sys.statusBarHeight

支付宝：my.getSystemInfo 无胶囊概念，
        但顶部仍有平台返回按钮，同样需留出避让区
抖音：  tt.getMenuButtonBoundingClientRect()，用法与微信一致
```

```javascript
// app.js 里算一次，全局复用
App({
  onLaunch() {
    const sys = wx.getWindowInfo();
    const menu = wx.getMenuButtonBoundingClientRect();
    this.globalData.navBar = {
      statusBarHeight: sys.statusBarHeight,
      navHeight: (menu.top - sys.statusBarHeight) * 2 + menu.height,
      totalHeight: (menu.top - sys.statusBarHeight) * 2 + menu.height + sys.statusBarHeight,
      menu
    };
  }
});
```

```
设计上的三条铁律：
├── 导航栏可点击元素一律靠左，右侧 200rpx 内不放任何可交互内容
├── 标题文字左对齐（居中会被胶囊挤成视觉偏右）
└── 返回箭头必须自己画（自定义导航栏后系统返回按钮消失），
    并确认 iOS 侧滑手势仍然可达：不要把整页做成横向可拖拽组件，
    否则用户在二级页面既没有可见返回、也滑不回去
```

**【专题补写】** 参考尺寸（**这些是常见机型的近似值，不同机型会变，务必用上面的 API 动态取值**）：胶囊宽约 87pt、高约 32pt、距屏幕右缘约 7-10pt；iPhone X 及以上状态栏约 44pt，iPhone 8 及安卓约 20-25pt。

### 3.3 安全区

```
需要避让的三个区域：

1. 顶部状态栏
   └── 全屏自定义导航时，用 statusBarHeight 撑开

2. 底部小黑条（Home Indicator，全面屏 iPhone）
   └── CSS：padding-bottom: env(safe-area-inset-bottom)
       兼容写法同时给 constant()：
       padding-bottom: constant(safe-area-inset-bottom);
       padding-bottom: env(safe-area-inset-bottom);
   └── 平台不会替页面根节点加底部内边距，
       "内容不贴底"要在设计稿阶段就留出来

3. 横屏/折叠屏
   └── 平板与折叠屏下 750rpx 会被拉得很宽，
       正文区需 max-width 约束（约 750-828px），否则一行 40 字
```

```css
/* 底部固定按钮的标准写法 */
.submit-bar {
  position: fixed;
  left: 0; right: 0; bottom: 0;
  padding-bottom: constant(safe-area-inset-bottom);
  padding-bottom: env(safe-area-inset-bottom);
}
/* 有 submit-bar 时，列表容器额外留 120rpx + 安全区 */
.scroll-view { padding-bottom: 120rpx; }
```

**【专题补写】** 安全区数值会因机型变化，代码里用 `env()` 取值而不是写死 34px；设计稿上按 iPhone 14 Pro（底部约 34pt）画留白即可。

### 3.4 包体与图片

```
包体限制（决定你怎么切页面和放图）：
├── 主包上限小，整包另有更大上限；超出必须走分包
├── 图片超过一定体积不能打进代码包，应放 CDN/云存储
└── 具体阈值三平台不同且会调整 → 见 02 的"目录结构与分包加载"
    并在提审前以官方文档为准复核

图片规范：
├── 位图用 WebP（小程序 image 组件支持），列表图走 CDN + 尺寸参数
├── 图标用 iconfont 而非一堆 png
│   └── 阿里巴巴矢量图标库 iconfont.cn 生成小程序可用的 base64 或字体文件
└── 设计稿导出：@2x 与 @3x 两套，命名统一
```

> 上述阈值属平台规则，见文末"需你复核的事实"。

**【专题补写】** 仓库尚未覆盖小程序组件库选型，本节为专题补写（P1）。

```

└── 适合：同一套 UI 要发多平台（对应 02 的 uni-app / Taro 路线）

├── 把 shadcn/ui / Ant Design / Element Plus 用在小程序里
│   └── 它们是 Web/React/Vue 栈，小程序不是 DOM 环境
├── 从零自研一整套组件库
│   └── OPC 的时间应该花在业务上；官方库 + 少量覆写足够
└── 用第三方"小程序 UI 框架大全"里长期无维护的项目
    └── 平台 API 一改就废，看最近一次 commit 时间
```

## 5. UX 原则与首屏质量线

### 5.1 UX 设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **即时反馈** | 用户操作后立即看到结果 | 按钮点击有动画，表单提交有成功提示 |
| **渐进披露** | 先展示核心，再展开高级 | 设置页面默认只显示常用选项 |
| **容错设计** | 允许用户犯错并轻松恢复 | 删除前有确认，操作可撤销 |
| **一致性** | 相同功能在不同页面表现一致 | 所有保存按钮都在右下角 |
| **可预测** | 用户能预判操作结果 | 点击头像出现下拉菜单（符合习惯） |

> 来源：`../super-individual/opc-product-design.md:201-207`

**【专题补写】** 小程序里"即时反馈"这一条权重最高，因为它有平台级原因：小程序冷启动需要下载代码包，用户本来就比打开 App 多等了一轮。任何一次点击后没有可见反馈，用户第一反应是"卡住了"而不是"在加载"，直接下拉退出。所以下面这四类操作**必须**有反馈，没有例外：网络请求、表单提交、权限申请、页面跳转。

### 5.2 设计决策清单

```
每个设计决策前问自己：

功能层面：
├── 这个功能是"必须有"还是" nice to have"？
├── 去掉这个功能，用户还能完成核心任务吗？
├── 这个功能会增加多少开发时间？
└── 这个功能会带来多少增量收入？

体验层面：
├── 新用户能在30秒内理解这个产品吗？
├── 核心任务能在3步内完成吗？
├── 错误提示是否清晰可行动？
└── 加载时间是否<2秒？

视觉层面：
├── 色彩是否符合品牌调性？
├── 字体是否易读？
├── 按钮是否明显可点击？
└── 移动端体验是否一致？

如果80%的答案都是"是"，就可以发布。
OPC不要追求100分的设计，70分足够验证。
```

> 来源：`../super-individual/opc-product-design.md:171-192`

### 5.3 发布前设计检查（10 分钟）

这是全专题的性能与体验口径基线，[02-development.md](./02-development.md) 的 setData 优化和 [03-operations.md](./03-operations.md) 的指标看板都对齐到这里。

```
视觉：
├── □ 所有页面风格一致
├── □ 移动端无水平滚动
├── □ 图片无拉伸/模糊
├── □ 按钮尺寸适合点击（最小44×44px）
└── □ 对比度符合WCAG标准

体验：
├── □ 空状态有引导内容
├── □ 加载状态有反馈
├── □ 错误提示清晰可行动
├── □ 表单有验证和提示
└── □ 退出前有保存提醒

性能：
├── □ 首屏加载<2秒
├── □ 交互响应<100ms
├── □ 无内存泄漏
└── □ 图片已压缩

转化：
├── □ CTA按钮明显
├── □ 定价页面清晰
├── □ 注册流程<3步
└── □ 支付流程顺畅
```

> 来源：`../super-individual/opc-product-design.md:413-437`（原文 `:411` 的"发布前设计检查（10分钟）"由本节标题承担）

**【专题补写】** 小程序里这条"首屏 < 2 秒"要拆成三段来看，否则你永远不知道慢在哪一段：

```
首屏 2 秒的构成：

冷启动 = 代码包准备 + 依赖加载 + 首页 setData + 首屏数据渲染

├── 代码包准备：平台侧，首次进入需下载，之后走缓存
│   └── 你能控制的只有包体大小 → 分包（见 02）
├── 首页 setData：本地渲染
│   └── 首屏 setData 数据量控制在极小范围，长列表分片（见 02 的 setData 一节）
└── 首屏数据请求：网络侧
    ├── 首页接口只返回首页可见字段，不要一次拉全量
    ├── 请求与渲染并行：先渲染骨架/缓存数据，回来再更新
    └── 弱网兜底：超过 2 秒未返回先出占位，不要白屏

优化优先级（收益/成本比从高到低）：
1. 首屏不做登录态判断以外的任何请求
2. 图片全部走 CDN + WebP + 懒加载
3. 分包（主包只放首页和公共库）
4. 首页数据本地缓存 + 静默更新
```

## 6. 用户旅程与 onboarding

### 6.1 用户旅程五阶段

```
发现阶段：
├── 触点：搜索/社媒/推荐
├── 目标：吸引注意力
├── 设计重点：Landing Page标题+CTA
└── 关键指标：点击率

注册阶段：
├── 触点：注册页面
├── 目标：降低注册门槛
├── 设计重点：社交登录、最少字段、即时价值
└── 关键指标：注册转化率

激活阶段：
├── 触点：产品首次使用
├── 目标：让用户完成"啊哈时刻"
├── 设计重点：引导流程、模板、快速获胜
└── 关键指标：激活率（完成核心行为的用户比例）

留存阶段：
├── 触点：日常使用
├── 目标：让用户形成习惯
├── 设计重点：通知、提醒、进度、成就
└── 关键指标：7日/30日留存率

推荐阶段：
├── 触点：使用后的分享
├── 目标：转化为传播者
├── 设计重点：分享按钮、邀请奖励、社交证明
└── 关键指标：NPS、邀请率

OPC重点：先做好激活和留存，再追求增长。
没有留存的增长是浪费。
```

> 来源：`../super-individual/opc-product-design.md:214-245`（原文 `:212` 的"用户旅程五阶段："由本节标题承担）

**【专题补写】** 把这套旅程映射到小程序，每一阶段的触点都要换掉：

| 阶段 | Web 触点 | 小程序触点 | 设计要额外做的事 |
|------|---------|-----------|----------------|
| 发现 | Landing Page | 搜一搜、扫码、群分享卡片、公众号菜单、附近的小程序 | 分享卡片的图与文案是"设计交付物"，必须出图（见第 7.2 节） |
| 注册 | 邮箱/社交登录 | 静默登录（`wx.login` 拿 code）+ 头像昵称用平台填写能力 | 小程序没有传统"注册页"：静默登录已能识别用户，头像昵称只在它有业务意义时才索要（接口现状与实现在 02） |
| 激活 | 引导教程 | 首屏模板 / 示例数据 | 空状态必须带一个"一键填充示例"按钮 |
| 留存 | Push / 邮件 | 订阅消息（一次性/长期） | 订阅消息授权只能由用户主动点击触发，设计稿里要预留触发时机（提交成功页最自然） |
| 推荐 | 邀请链接 | `onShareAppMessage` + 分享图片 | 分享出去的图不带二维码，靠小程序卡片本身回流 |

### 6.2 Onboarding 三步法

```
新用户引导三步法：

Step 1：欢迎（30秒）
├── 个性化问候（"欢迎，[名字]！"）
├── 一句话价值主张
├── 3步预览（"只需3步，你就可以..."）
└── 提供跳过选项（不要强迫）

Step 2：快速获胜（2分钟）
├── 引导完成第一个核心任务
├── 提供模板/示例降低创作成本
├── 实时反馈和鼓励
└── 目标：让用户在2分钟内感受到价值

Step 3：探索（持续）
├── 功能提示（在合适时机展示）
├── 进度条（"你已完成了80%设置"）
├── 空状态设计（引导用户填充内容）
└── 帮助入口（随时可找到）

优秀的 onboarding 示例：
├── Notion：模板库让你立即创建第一页
├── Canva："你想设计什么？"引导选择模板
├── Figma：实时协作演示
└── 核心原则：让用户在首次使用就获得价值
```

> 来源：`../super-individual/opc-product-design.md:251-275`

**【专题补写】** 小程序 onboarding 与 App 有三点结构性差异，照搬上面三步法会踩坑：

```
1. 用户是从一个具体场景被"抛进来"的
   群分享、扫码、搜一搜进入的首页可能根本不是你的引导页。
   → 引导流程挂在"冷启动首次进入"这个本地标记上，
     而不是挂在某个页面上；否则分享深链进来的用户会被引导打断。

2. 授权弹窗不是引导的一部分
   微信的隐私授权、位置授权、订阅消息授权都必须在用户已经理解
   "我要这个权限是为了什么"之后出现。
   → 设计稿里给每个权限画一个"前置说明页/半屏弹层"，
     说明用途 + 拒绝后仍能用的功能。（合规要求见 06）

3. 没有第二次冷启动机会
   小程序是场景驱动的：搜一搜、扫码、群卡片把人带进来，用完即走，
   它没有 App 那种"每天主动打开一次"的使用心智。
   而下次进来时平台会保留上次状态，不会再走一遍引导。
   → 关键引导只做一次，因此"2 分钟内感受到价值"在小程序上比在 App 上更致命。
```

> 政策快照｜截至 2026 年 10 月。平台规则会调整，发布前请核对官方文档，以官方为准。

## 8. 产品迭代节奏

```
OPC产品迭代SOP：

双周迭代制：
Week 1：
├── 周一：review反馈，确定本周优先级
├── 周二-四：开发（Vibe Coding加速）
├── 周五：内部测试
└── 周末：休息

Week 2：
├── 周一：修复Bug，优化体验
├── 周二：发布更新
├── 周三-四：观察数据，收集反馈
└── 周五：规划下周

月度大版本：
├── 每月最后一周发布大功能
├── 提前在社群预热
├── 发布日配合内容营销
└── 发布后续航监控

季度复盘：
├── 回顾核心指标变化
├── 分析成功/失败功能
├── 调整产品路线图
└── 更新年度目标
```

> 来源：`../super-individual/opc-product-design.md:378-403`

**【专题补写】** 小程序不能照抄这个节奏，因为**"周二发布更新"这一步在小程序上要变成"周二提审"**：

```
小程序版双周迭代：

Week 1 与上面一致（开发 + 内测）

Week 2：
├── 周一：修 Bug、体验优化
├── 周二上午：提审（留出当天被驳回后重提的余量）
├── 周二-周四：审核期。不空等——本地继续开发下一个迭代
├── 审核通过：先小流量放开（灰度做法见 03），不要一次性全量
└── 周五：规划下周

节奏上的两条硬约束：
1. 审核时长不可控。多数在 1-7 天区间内波动，
   涉及资质、类目、支付的版本通常更慢。
   → 永远不要把发布日承诺给到"提审当天"。
2. 线上版本无法即时回退。小程序后台只能提新版本覆盖，
   不能用一个按钮退回上一个版本。
   → 出问题时的止血手段是服务端配置开关而不是版本回滚，
     这就是设计阶段要预留 killSwitch 的原因（见 03 的回滚一节）。
```

> 政策快照｜截至 2026 年 10 月。平台规则会调整，发布前请核对官方文档，以官方为准。

**【专题补写】** 这条节奏在 OPC 社群调研里有一条对应的失败数据支撑：**"没有持续迭代，发布后放任"占失败者特征 60%**（数据与口径见 [04-growth.md](./04-growth.md) 第 13.1 节）。把双周节奏当成硬性纪律而不是弹性建议，原因就在这条数据上。小程序还有一个加重因素：**平台不会因为你不更新就把小程序下架，但同类产品在更新时你会被比下去**。搜一搜等入口的排序参考使用数据与活跃度，而小程序不像 App Store 那样有"版本历史 / 更新说明"这类可以事后补回来的公开资产——更新记录本身就是转化材料的一部分，这里没有。所以发布后的两周一次小迭代，在这个渠道里同时承担"产品维护"和"渠道存在感"两件事。

## 9. 与 Web 设计系统的差异

`../super-individual/opc-product-design.md:282-314` 给出的"OPC 最小可行设计系统"推荐方案是 **shadcn/ui（Next.js/React）、Ant Design（React）、Element Plus（Vue）、Tailwind UI**。这套内容原样保留在原文中，本专题不搬，因为它对小程序不成立：

```
为什么不成立：

运行环境
├── Web 设计系统假设你有 DOM，可以任意 CSS、任意三方包
└── 小程序是平台容器内的受限渲染层：
    没有 document / window，标签不是 HTML，样式选择器能力受限

组件模型
├── React/Vue 组件是函数 + 虚拟 DOM
└── 小程序组件是 wxml + wxss + js + json 四件套，
    跨框架不能直接 import

样式方案
├── Tailwind 依赖构建产物与 utility class
└── 小程序里同样能做原子类，但要自己配构建，
    收益远不如直接用官方组件库

结论（对应第 4 节）：
├── 单平台 → 微信 WeUI / 支付宝 antd-mini
├── 组件不够 → Vant Weapp，按需引入
├── 多端一致 → TDesign + uni-app 或 Taro（选型决策树见 02）
└── 上面那套 Web 设计系统留给你将来做官网和 Web 版产品时使用
```
