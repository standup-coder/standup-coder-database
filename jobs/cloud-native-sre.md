# 云原生SRE工程师(Kubernetes/ACK方向)职位描述(JD)

## 岗位基本信息
- **岗位名称**：云原生SRE工程师(Cloud Native SRE / Kubernetes SRE)
- **岗位定位**：云原生运维底座层 - 容器平台稳定性保障
- **工作性质**：全职(需承担7x24 On-Call轮值)
- **工作地点**：杭州/北京/上海/深圳/成都
- **招聘人数**：若干
- **薪资范围**：30K-75K/月
- **团队规模**：容器服务SRE团队30-150人，单集群方向小组5-15人

## 公司与行业背景

### 行业背景
Kubernetes已成为企业级基础设施的事实标准，公有云容器服务(ACK/TKE/CCE)托管着数十万级生产集群。随着AI训练/推理负载大规模上云，容器平台从"无状态Web应用底座"演进为"GPU异构算力调度底座"，SRE的职责边界从传统的可用性保障扩展到算力效率、大规模节点池弹性、多租户隔离等新场景。头部云厂商容器SRE团队正在经历"人肉排障→自动化→智能体辅助运维"的代际升级，具备K8s内核级排障能力的SRE持续供不应求。

## 岗位职责

### 集群稳定性保障
- 负责大规模Kubernetes集群(ACK)的稳定性保障与SLO管理
- 保障APIServer/etcd/Scheduler等控制面组件的高可用与性能
- 处理节点异常、网络抖动、存储故障等数据面问题
- 建设集群巡检、风险预警与容量水位管理体系
- 主导P1/P2级故障应急响应与复盘改进

### 运维自动化与自愈体系
- 开发集群运维自动化工具(节点自愈、证书轮转、版本升级流水线)
- 建设基于Operator模式的运维能力(自定义CRD/Controller)
- 实现故障自动诊断与分级自愈(节点隔离、Pod驱逐、流量切换)
- 沉淀标准化运维SOP并推动SOP代码化/工具化
- 参与ChatOps与运维智能体的场景接入(诊断工具封装为Agent可调用能力)

### 可观测性体系建设
- 建设Metrics/Logging/Tracing三位一体可观测体系
- 优化Prometheus大规模指标采集与存储成本
- 设计面向SLO的告警策略并治理告警风暴
- 建设eBPF深度观测能力(网络流/系统调用级问题定位)

### AI负载场景支撑
- 支撑GPU节点池的调度、监控与故障处理(XID错误、掉卡、ECC)
- 保障AI训练/推理负载的网络(RDMA)与存储(CPFS)稳定性
- 优化大规模弹性伸缩场景(训练任务潮汐、推理突发流量)

### 变更与容量管理
- 制定集群版本升级、组件变更的灰度策略与回滚预案
- 执行混沌工程演练验证系统韧性
- 完成成本优化(资源画像、超卖策略、闲置回收)

## 面试准备建议

### 高频面试题
1. **控制面排障**：APIServer延迟突增，从哪些维度定位？etcd的哪些指标是关键信号？
2. **节点问题**：节点NotReady的完整排查链路是什么？如何设计节点自愈的安全护栏(避免雪崩式驱逐)？
3. **SLO设计**：如何为一个托管K8s服务定义SLI/SLO？错误预算耗尽后的决策机制如何运作？
4. **大规模挑战**：5000节点集群中，List-Watch风暴如何产生？如何从客户端与服务端两侧治理？
5. **GPU场景**：GPU节点频繁掉卡，如何建立从硬件信号(XID/ECC)到自动隔离换卡的闭环？

### 系统设计题
- 设计一个支持万级集群的巡检与风险预警平台
- 设计K8s集群跨可用区容灾与故障切换方案
- 设计一套变更灰度体系(分批、熔断、自动回滚)
- 设计面向运维智能体的诊断工具API规范

### 实操考察
- 现场排查一个故障场景(如Pod Pending/CrashLoopBackOff的多层原因)
- Go编写一个简单Controller(监听资源变化并执行动作)
- 阅读一段Kubelet/Scheduler源码并解释行为

### 面试流程
1. **HR初筛**(30分钟)
2. **技术一面**(1-1.5小时)：K8s原理深度 + 排障实战
3. **技术二面**(1.5小时)：工程能力 + 系统设计
4. **交叉面/三面**(1小时)：稳定性方法论与项目深挖
5. **HRBP终面**：整体周期2-3周
