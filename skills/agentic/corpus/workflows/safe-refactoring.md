# 工作流：安全重构

重构的定义是**行为不变、结构变好**。agent 做重构很有优势（不厌烦、不遗漏），前提是给它装上"行为不变"的客观判据和可回退的提交节奏。

## 步骤

### 1. 锚定基线

- 跑全量测试，确认全绿；把输出存档。
- 没有测试覆盖的部分，先用[特征测试（golden test）](#什么是特征测试)锁住当前行为。

### 2. 小步提交，每步一个变换

一个提交只做一类变换，按风险从低到高：

1. 改名 / 提取函数 / 提取常量
2. 移动文件与模块边界调整
3. 改数据结构 / 改接口内部签名

每步后跑测试，绿了才提交。**提交信息写清变换类型**（`refactor: extract parseUser from handler`）。

### 3. 让 agent 执行，你来把关每一步

> "执行重构：<目标>。约束：一次只做一类变换；每步变换后运行 `<测试命令>`，必须全绿才能进入下一步；任何一步红了，回退该步并报告，不要绕过。"

**人工检查点**：每 2-3 步抽查 `git diff`——agent 最常见的失败模式是"顺手修了一个测试"，那意味着行为变了。

### 4. 收尾对账

- `git diff <起点>...HEAD` 里不应出现任何行为相关改动（新 if 分支、新默认值）。
- 测试数量：重构前后一致（除非特征测试被真实测试替代）。

## 什么是特征测试

给**现有**（未设计的）行为补的测试：不管当前行为对不对，先照实断言。作用是把"重构改变了行为"从静默错误变成红灯。重构完成后再人工评审这些行为该不该改。

## 常见坑

- **测试红了让 agent"修测试"**：先问"行为变了吗？"——变了就是重构做错了，改的应该是实现，不是测试。
- **一步迈太大**：`git revert` 单个大提交很痛，单个 5 分钟的小提交几乎无痛。
- **在重构提交里混入功能改动**：混了就无法回退也无法 review，见[提交前检查清单](../checklists/before-commit.md)。
