# 故障管理与On-Call实战指南

## 一、故障分级体系

### P0-P4定义标准

| 等级 | 定义 | 影响范围 | 响应时间 | 恢复目标 | 升级路径 |
|------|------|----------|----------|----------|----------|
| P0 | 全站不可用/数据丢失 | 全部用户 | 5分钟内 | 30分钟 | 立即通知CTO/CEO |
| P1 | 核心功能不可用 | >30%用户 | 15分钟内 | 1小时 | 15分钟通知技术VP |
| P2 | 重要功能降级 | 10-30%用户 | 30分钟内 | 4小时 | 30分钟通知总监 |
| P3 | 非核心功能异常 | <10%用户 | 2小时内 | 24小时 | 次日通知Team Lead |
| P4 | 体验问题/边缘Case | 极少用户 | 下一工作日 | 下一迭代 | 工单跟踪 |

### 升级路径设计
- **一级响应**：On-Call工程师（5分钟内确认）
- **二级升级**：15分钟未解决 → 升级至Team Lead + 相关领域专家
- **三级升级**：30分钟未解决 → 升级至总监 + 启动War Room
- **四级升级**：1小时未解决 → 升级至VP/CTO + 启动对外通报
- **原则**：升级不等于追责，是为了获取更多资源和决策权

## 二、On-Call体系

### 轮转设计
- **团队规模**：至少5人一组（保证每人每月On-Call不超过1周）
- **轮转周期**：推荐1周轮转（周一10:00交接），避免周末交接
- **主备制度**：Primary + Secondary，Primary 5分钟无响应自动升级Secondary
- **跨时区**：Follow-the-Sun模式，减少夜间打扰
- **新人保护**：入职3个月内不独立On-Call，需Shadow至少2个周期

### 交接流程
- **交接会议**（30分钟）：
  - 当前未关闭告警及状态
  - 近期变更（部署、配置、基础设施）
  - 已知风险点和观察项
  - 特殊注意事项（大促、客户活动）
- **交接文档**：标准化模板，记录在共享Wiki
- **交接确认**：双方在系统中确认交接完成

### 补偿机制
- **值班补贴**：工作日On-Call 200-500元/天，周末/节假日翻倍
- **夜间响应**：每次夜间被叫醒额外补贴（无论是否实际处理）
- **调休制度**：P0/P1故障处理后次日可半天调休
- **长期激励**：On-Call表现纳入晋升评估（体现Ownership）

### 心理健康
- **告警疲劳**：每月告警数 > 50条需治理，目标 < 20条可操作告警
- **创伤后压力**：重大故障后提供心理支持，不强制立即复盘
- **轮换保护**：连续处理2次P0后强制休息1天
- **文化建设**：On-Call是团队责任而非个人惩罚，感谢而非指责

## 三、响应流程（黄金30分钟）

### 完整响应链路

```
发现(0-5min) → 确认(5-10min) → 止血(10-30min) → 修复(30min-4h) → 复盘(24-72h)
```

### 阶段一：发现（0-5分钟）
- **监控告警**：自动化告警触发（PagerDuty/钉钉/飞书）
- **人工发现**：用户反馈、客服上报、内部巡检
- **关键动作**：确认告警真实性（排除误报），记录发现时间

### 阶段二：确认（5-10分钟）
- **影响评估**：影响哪些用户？哪些功能？影响程度？
- **初步定界**：是网络/应用/数据库/第三方？
- **宣布故障**：在故障频道发布初始信息，指定Incident Commander（IC）
- **IC职责**：协调资源、管理通信、做决策（不亲自修Bug）

### 阶段三：止血（10-30分钟）
- **优先止血而非根因**：回滚 > 降级 > 限流 > 切流
- **止血手段优先级**：
  1. 回滚最近变更（80%故障由变更引起）
  2. 开启降级开关（关闭非核心功能）
  3. 流量切换（主备切换、多活切流）
  4. 限流熔断（保护核心链路）
- **决策原则**：如果5分钟内无法确定根因，先回滚/降级

### 阶段四：修复（30分钟-4小时）
- **根因分析**：日志、监控、变更记录、依赖排查
- **修复方案**：制定方案 → 评审 → 灰度验证 → 全量
- **持续通报**：每30分钟更新进展
- **恢复确认**：监控指标恢复正常 + 人工验证核心场景

### 阶段五：复盘（24-72小时内）
- 详见第六节"复盘"部分


## 五、SLO/SLI/SLA

### 定义方法
- **SLI（服务等级指标）**：可量化的服务指标
  - 可用性：成功请求数 / 总请求数
  - 延迟：P99响应时间
  - 吞吐量：每秒处理请求数
  - 正确性：返回正确结果的比例
- **SLO（服务等级目标）**：内部目标（通常严于SLA）
  - 示例：可用性 99.95%（月度）= 每月允许21.6分钟不可用
- **SLA（服务等级协议）**：对外合同承诺（违反有赔偿）
  - 示例：可用性 99.9%，低于则赔偿10%月费

### Error Budget（错误预算）
- **计算**：1 - SLO = 错误预算（99.95% SLO → 0.05%预算）
- **用途**：
  - 预算充足 → 可以激进发布新功能
  - 预算耗尽 → 冻结发布，专注稳定性
- **协商**：与产品团队共享Error Budget仪表盘，用数据平衡速度与稳定性

### 与产品协商
- **原则**：SLO不是技术团队单方面决定，需要产品确认"用户可接受的体验"
- **方法**：从用户旅程出发定义关键路径，不同路径不同SLO
- **示例**：支付页面 99.99%，推荐列表 99.9%，后台报表 99.5%

## 六、复盘（Postmortem）

### 无责复盘文化
- **核心理念**：人会在任何系统中犯错，目标是让系统更健壮
- **禁止**：指名道姓追责、"谁干的"、"为什么没检查"
- **鼓励**：描述行为和系统缺陷、"流程哪里允许了这个错误发生"
- **领导示范**：管理者先分享自己的失误，建立心理安全

### 5-Why分析法
```
问题：用户无法支付
Why1：支付网关超时
Why2：数据库连接池耗尽
Why3：慢查询占用连接未释放
Why4：新上线的报表查询未加索引
Why5：代码审查未覆盖SQL性能 + 缺少慢查询告警
改进：①SQL Review Checklist ②慢查询自动告警 ③连接池监控
```

### 时间线模板
| 时间 | 事件 | 操作人 |
|------|------|--------|
| 14:00 | 配置变更推送 | 系统自动 |
| 14:32 | 监控告警触发 | PagerDuty |
| 14:35 | On-Call确认故障 | 工程师A |
| 14:38 | 宣布P1，建立War Room | IC张三 |
| 14:45 | 决定回滚配置 | IC张三 |
| 15:10 | 回滚完成，观察恢复 | 工程师B |
| 15:28 | 确认完全恢复 | IC张三 |

### Action Items管理
- **格式**：具体行动 + 负责人 + 截止日期 + 验收标准
- **跟踪**：录入项目管理工具，下次故障周会Review
- **闭环**：超期未完成的Action Item自动升级至总监
- **有效性验证**：改进措施实施后，验证是否真正降低了同类故障概率

- **自动化**：高频操作脚本化（一键回滚、一键切流）

## 八、混沌工程

### 核心理念
- **定义**：在生产/预发环境主动注入故障，验证系统韧性
- **原则**：从最小爆炸半径开始、有明确假设、可快速终止
- **目标**：发现隐患于故障发生之前，而非之后

### 工具
| 工具 | 来源 | 能力 |
|------|------|------|
| Chaos Monkey | Netflix | 随机终止实例 |
| ChaosBlade | 阿里开源 | CPU/内存/网络/进程故障注入 |
| LitmusChaos | CNCF | Kubernetes原生混沌工程 |
| Gremlin | 商业 | 企业级混沌工程平台 |
| AWS FIS | AWS | AWS原生故障注入 |

### GameDay演练
- **频率**：季度一次（至少），核心系统月度
- **流程**：
  1. 制定演练计划（场景、范围、终止条件）
  2. 通知相关方（但不透露具体时间）
  3. 注入故障，观察团队响应
  4. 记录时间线、决策点、改进机会
  5. 复盘并输出Action Items
- **典型场景**：
  - 主数据库宕机，验证自动切换
  - CDN节点故障，验证回源能力
  - 核心依赖服务超时，验证降级策略
  - 机房级故障，验证多活切换

## 九、典型案例

### 案例一：数据库主从切换故障
- **现象**：主库OOM触发自动切换，新主库延迟30秒，部分写入丢失
- **根因**：大事务导致主库内存暴涨；从库复制延迟未监控
- **改进**：大事务拆分、复制延迟告警（>5秒）、应用层重试机制

### 案例二：CDN故障
- **现象**：CDN供应商节点异常，静态资源404，页面白屏
- **根因**：单一CDN供应商、无回源降级策略
- **改进**：多CDN互备、本地缓存兜底、CDN健康检查自动切换

### 案例三：配置推送事故
- **现象**：配置中心推送错误配置，全量服务同时生效，核心接口500
- **根因**：配置变更无灰度、无校验、无快速回滚
- **改进**：配置灰度推送（1%→10%→100%）、配置Schema校验、一键回滚

### 案例四：容量不足
- **现象**：大促流量超预期3倍，服务雪崩
- **根因**：容量评估基于历史数据未考虑营销爆发、无弹性扩容
- **改进**：大促前压测（目标2倍峰值）、HPA自动扩容、限流预案

## 十、度量与持续改进

### 核心指标
| 指标 | 定义 | 目标 |
|------|------|------|
| MTTD（平均发现时间） | 故障发生到被发现的时间 | < 5分钟 |
| MTTR（平均恢复时间） | 故障发现到恢复的时间 | P0 < 30分钟 |
| MTBF（平均故障间隔） | 两次故障之间的平均时间 | 逐季提升 |
| 变更失败率 | 导致故障的变更占比 | < 5% |
| 告警准确率 | 真实故障 / 总告警数 | > 80% |

### 故障频率趋势
- **月度Review**：故障数量、等级分布、MTTR趋势
- **季度分析**：故障类型分布（变更/容量/依赖/人为）、重复故障率
- **年度目标**：P0/P1故障数量同比下降30%、MTTR同比下降20%

### 改进跟踪
- **Action Item完成率**：目标 > 90%（30天内）
- **改进有效性**：同类故障是否再次发生
- **成熟度评估**：
  - Level 1：被动响应（救火）
  - Level 2：有流程（On-Call + 复盘）
  - Level 3：主动预防（监控 + 混沌工程）
  - Level 4：自愈系统（自动检测 + 自动恢复）
  - Level 5：持续优化（数据驱动 + 预测性维护）

---

> **核心原则**：故障不可避免，但可以从每次故障中学习。目标不是零故障，而是让系统越来越韧性、响应越来越快、影响越来越小。
