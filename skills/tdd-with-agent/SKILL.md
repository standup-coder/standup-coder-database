# TDD 循环

用红-绿-重构循环开发。目的：让每一步都有客观判据，防止"声称完成但未经验证"。

## 循环

1. **红**：为一个行为写一个会失败的测试。只写测试，不写实现。运行它，向用户展示失败输出，并确认失败原因是"行为缺失"而非测试自身的错误。
2. **绿**：用最小实现让该测试通过。不改其他测试，不做计划外重构。运行全量测试并展示结果。
3. **重构**：绿灯下做用户指名的清理。每步重构后跑测试，红了回退该步，不绕过。

一次循环只覆盖一个行为。多个行为 = 多次循环。

## 对修 bug 的特殊规则

先写**复现测试**（红），再修（绿）。没有复现测试的 bug 修复不得提交——无法证明修复命中了问题，也无法防止回归。

## 测试写法要求

- 断言外部可观察行为（返回值、渲染结果、状态变化），不断言内部调用顺序等实现细节。
- 测试名说清"什么条件下发生什么"。
- 不为了让测试通过而修改生产代码之外的断言。

## 禁止

- 批量写完所有测试再写实现。
- 在红-绿循环中顺手重构。
- 声称"测试通过"而未实际运行并向用户展示输出。
- 修改测试使其迁就不正确的行为（测试错应说明并征得同意）。
