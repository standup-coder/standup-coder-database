# 开源许可证选择与合规指南

## 概述

开源许可证是开源软件的法律基础，决定了代码如何被使用、修改和分发。选择合适的许可证不仅影响项目的采用率，还关系到商业模式的可行性。本指南从分类、选择、合规和风险四个维度进行全面梳理。

## 许可证分类体系

### 宽松型许可证（Permissive）

| 许可证 | 特点 | 代表项目 |
|--------|------|---------|
| MIT | 最简短，几乎无限制 | Vue.js, React, jQuery |
| BSD-2/3-Clause | 类似MIT，3-Clause含反背书条款 | Nginx, FreeBSD |
| Apache-2.0 | 含专利授权条款，企业友好 | Kubernetes, Android |
| ISC | MIT的简化版 | OpenBSD, npm |
| Unlicense | 完全放弃版权，进入公有领域 | sqlite(部分) |

### Copyleft许可证（强/弱著佐权）

| 许可证 | 传染性 | 特点 | 代表项目 |
|--------|--------|------|---------|
| GPL-2.0 | 强 | 衍生作品必须同许可 | Linux Kernel |
| GPL-3.0 | 强 | 增加反Tivo化、专利条款 | GCC, GIMP |
| AGPL-3.0 | 最强 | 网络使用也触发开源 | MongoDB(旧), Grafana |
| LGPL-2.1/3.0 | 弱 | 库链接不传染 | Qt, glibc |
| MPL-2.0 | 文件级 | 修改的文件需开源，新文件不受限 | Firefox, Terraform |

### 源码可用但非开源（Source Available）

| 许可证 | 限制 | 代表项目 |
|--------|------|---------|
| BSL 1.1 | 商业使用需付费，N年后转开源 | MariaDB, Redis(2024后) |
| SSPL | 提供SaaS需开源全部服务栈 | MongoDB(2018后) |
| CC BY-NC | 禁止商业使用 | 部分文档/数据集 |
| Elastic License 2.0 | 禁止托管服务 | Elasticsearch(2021后) |
| 木兰宽松(MulanPSL-2.0) | 类似Apache-2.0，中国法律适用 | OceanBase |

## 许可证选择指南

### 按项目类型推荐

| 场景 | 推荐许可证 | 理由 |
|------|-----------|------|
| 通用工具库/SDK | MIT | 最大化采用率，无法律负担 |
| 企业级框架 | Apache-2.0 | 专利保护，企业法务友好 |
| 希望衍生也开源 | GPL-3.0 | 强Copyleft确保生态开源 |
| SaaS/云服务 | AGPL-3.0 或 SSPL | 防止云厂商白嫖 |
| 文件级共享 | MPL-2.0 | 平衡开源与商业扩展 |
| 学术/研究 | Apache-2.0 或 MIT | 便于学术引用和二次开发 |
| 商业化双许可 | MPL-2.0 或 自定义 | 社区版开源+企业版商业 |
| 中国法律环境 | MulanPSL-2.0 | 中文法律文本，中国法院管辖 |

### 决策流程图

```
是否希望所有衍生品必须开源？
├── 是 → 是否涉及网络服务？
│   ├── 是 → AGPL-3.0
│   └── 否 → GPL-3.0
└── 否 → 是否需要专利保护？
    ├── 是 → Apache-2.0
    └── 否 → 是否在中国法律环境？
        ├── 是 → MulanPSL-2.0
        └── 否 → MIT
```

## 中国特色：木兰许可证体系

### 木兰宽松许可证（MulanPSL-2.0）

- **发布方**：中国开源软件推进联盟（COPU），2020年发布
- **特点**：
  - 中英文双语，以中文为准
  - 类似Apache-2.0，含明确专利授权
  - 适用中国法律，中国法院管辖
  - 已通过OSI认证（2021年）
- **使用项目**：OceanBase、openEuler、部分华为项目

### 木兰Copyleft许可证（MulanPSL-Copyleft）

- 类似GPL-3.0的强Copyleft
- 适用于希望强制开源的场景
- 目前采用率较低，主要在政府/国企项目中出现

### 合规必备文件

1. **LICENSE文件**：项目根目录放置完整许可证文本
2. **NOTICE文件**：Apache-2.0要求，列出第三方归属
3. **版权声明头**：源文件顶部添加版权和许可声明
4. **CHANGELOG**：记录许可证变更历史
5. **依赖清单(SBOM)**：Software Bill of Materials，列出所有依赖及许可证

### 合规流程

```
代码引入 → 许可证识别 → 兼容性检查 → 审批流程 → 归档记录
     ↓
定期审计 → 依赖更新 → 许可证变更检测 → 重新评估
```

## 常见风险与应对

### GPL传染性风险

- **风险**：在闭源产品中链接GPL库，整个产品需开源
- **应对**：使用LGPL替代、进程隔离、或购买商业许可
- **案例**：VMware被诉使用Linux内核代码

### AGPL网络触发

- **风险**：通过网络提供服务即触发开源义务，无需分发
- **应对**：避免在SaaS产品中使用AGPL组件，或使用MongoDB Atlas等商业版
- **案例**：多家云厂商因AGPL放弃MongoDB，催生SSPL

### 双许可策略

- **模式**：社区版GPL/AGPL + 企业版商业许可
- **代表**：MySQL(Oracle)、Qt、MongoDB
- **注意**：需要CLA收集贡献者版权，否则无法单方面更改许可

### CLA vs DCO

| 维度 | CLA(贡献者许可协议) | DCO(开发者原创证书) |
|------|-------------------|-------------------|
| 版权 | 贡献者授予/转让版权给项目 | 贡献者保留版权，仅声明原创 |
| 许可证变更 | 项目方可单方面变更 | 需所有贡献者同意 |
| 复杂度 | 需签署法律文件 | 仅需Signed-off-by |
| 代表 | Apache基金会, Google | Linux Kernel, GitLab |

## 企业OSPO建设

### 开源治理办公室（OSPO）职能

1. **政策制定**：开源使用政策、贡献政策、发布政策
2. **合规审查**：入站代码许可证审查、出站发布合规
3. **依赖管理**：建立许可证白名单/黑名单/灰名单
4. **贡献管理**：员工参与开源的审批和激励
5. **风险管控**：许可证冲突预警、诉讼应对

### 许可证分级管理

| 级别 | 许可证 | 使用条件 |
|------|--------|---------|
| 白名单 | MIT, BSD, Apache-2.0, ISC | 自由使用 |
| 灰名单 | LGPL, MPL-2.0 | 需法务审批 |
| 黑名单 | GPL, AGPL, SSPL | 禁止用于闭源产品 |
| 特殊 | BSL, CC-NC | 逐案评估 |

## 经典案例分析

### Vue.js许可证变更

- 2024年Vue讨论从MIT转向更可持续的许可模式
- 最终保持MIT，但通过赞助和Open Collective维持运营
- 启示：许可证变更影响巨大，社区信任是核心资产

### Redis许可证变更（2024）

- Redis从BSD-3变更为RSALv2和SSPLv1双许可
- 不再符合OSI开源定义
- Linux基金会fork出Valkey项目（BSD许可）
- 启示：源码可用≠开源，社区可能fork

### Elasticsearch与SSPL

- 2021年Elasticsearch从Apache-2.0转为SSPL+Elastic License
- AWS fork出OpenSearch（Apache-2.0）
- 2024年Elastic回归AGPLv3+商业双许可
- 启示：许可证变更可能催生竞争对手

### 华为木兰许可证

- 2019年华为发布木兰许可证体系
- 2021年MulanPSL-2.0获OSI认证
- openEuler、OceanBase等项目采用
- 启示：中国需要自主可控的许可证体系

## 最佳实践总结

1. **新项目**：优先选择Apache-2.0（企业友好+专利保护）或MIT（极简）
2. **引入依赖**：建立许可证白名单，CI中集成自动检查
3. **发布产品**：生成SBOM，保留NOTICE和版权声明
4. **商业产品**：避免GPL/AGPL依赖，或购买商业许可
5. **贡献上游**：确认CLA/DCO要求，企业需内部审批
6. **许可证变更**：提前6个月公告，提供迁移路径，尊重社区
