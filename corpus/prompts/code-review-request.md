# 提示词模板：请 agent 做代码审查

## 何时用

自己（或 agent）刚写完一段代码，提交前想让人/agent 用挑剔的眼光过一遍。比"帮我看看这段代码"有效得多——限定角色、范围和输出格式，审查质量会明显提高。

## 模板

```text
角色：你是资深工程师，正在 review 同事的 PR，任务是找问题，不是夸奖。
范围：只审查 <文件/目录或 diff 范围>，本次改动意图是 <一句话>。
审查维度（按优先级）：
1. 正确性：逻辑错误、边界条件、并发/异步问题
2. 安全：注入、越权、敏感信息泄漏
3. 健壮性：错误处理、资源释放、空值
4. 可读性：命名、重复代码、超长函数
输出格式：
- 每条问题 = 文件:行号 + 一句话问题 + 一句话建议
- 按严重程度标 P0（必须改）/ P1（应该改）/ P2（可选）
- 结尾给一行总结：可以合并 / 需要修改后合并
不要：重写整段代码，不要评论本次改动之外的存量代码。
```

## 变量说明

| 变量 | 说明 |
| --- | --- |
| 范围 | 给 diff（`git diff main...HEAD`）比给整个目录效果好，能聚焦本次改动 |
| 改动意图 | 一句话即可，让 reviewer 区分"故意的"和"写错的" |
| 审查维度 | 按项目性质增删：前端可加可访问性，库代码可加 API 设计 |

## 提示

- P0/P1/P2 分级是关键：没有分级的审查清单会让你不知道先改哪个。
- 审查意见有分歧时，要求 agent"给出该判断所依据的代码或文档证据"，不要接受无证据的断言。
- 审查通过 ≠ 不用跑测试，提交前仍走[提交前检查清单](../checklists/before-commit.md)。
