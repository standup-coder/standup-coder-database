# 系统化调试

目标是最小化"猜测-返工"循环。铁律：**先定位根因，再改代码。**

## 流程

1. **固化现象**：拿到完整报错原文、复现步骤、期望行为。信息不足时先向用户要（报错原文必须原文贴出，不接受转述）。
2. **收集证据**：阅读相关代码与日志，用可运行的观察（打印、断点、最小脚本）缩小范围。每一步记录"观察到了什么"。
3. **列出假设**：基于证据列出 2-3 个候选根因，按可能性排序。对每个假设说明：支持它的证据、能证伪它的检验。
4. **检验假设**：一次检验一个，从最便宜的开始（看代码 > 加日志 > 写复现脚本）。检验结果更新假设列表。
5. **定位根因后**：先向用户报告根因 + 修复方案，确认后再动手。若根因暴露出系统性问题（如无类型校验的 `any` 边界），提出根源修复建议供用户决定。
6. **修复并防回归**：写复现测试（先红后绿，见 tdd-with-agent），再实施修复。展示修复前后的对比证据。

## 红线

- 不得在假设未验证时修改代码"试试看"。
- 不得用删除测试、放宽断言、try-catch 吞错等方式让症状消失。
- 不得在无证据时宣布"已修复"——修复 = 复现测试由红变绿 + 全量测试通过，两项都有输出证明。
