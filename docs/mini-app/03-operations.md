# 小程序运维

小程序的运维对象和你想的不一样：没有主机、没有部署、没有进程。本文件把"运维"重新定义为：埋点、度量、发布节奏、异常发现与止血，以及一个人撑得住的故障分级与账单。仓库里的团队故障手册结构可以直接借，但每一处时限都要按"只有你一个人"重算。

## 运维对象与边界

**【专题补写】** 先把边界划清，否则会照着服务器运维那套去准备，白准备。

| 维度 | 原生 App / 自建服务 | 小程序 |
|------|--------------------|--------|
| 运行载体 | 你的 APK/IPA + 你的服务器 | 平台宿主 App（微信/支付宝/抖音） |
| 部署 | 你自己发布 | 平台审核 + 平台下发 |
| 主机/容器 | 需运维 | 不存在（或云开发托管） |
| 回滚 | 秒级重新部署 | **需重新走审核**，分钟到小时级 |
| 崩溃监控 | Crashlytics/Bugly SDK | 平台自带 + 前端 try/catch |
| 版本共存 | 长期共存多版本 | 基本只有最新版（缓存版本短暂共存） |
| 客户端发版节奏 | 你决定 | 被审核周期约束 |
| 真正在你手里 | 全部 | **只有后端接口 + 配置项** |

结论：小程序运维的重心是**后端可用性**与**配置开关**。前端出问题你无法热修，只能靠开关关掉坏功能，或等审核。

你的运维清单实际只有四项：

```bash
1. 后端接口可用性与延迟（这是 90% 小程序故障的真实来源）
2. 服务端配置下发（功能开关、灰度比例、兜底文案）
3. 数据埋点质量（埋点断了你会瞎掉，且往往几天后才察觉）
4. 平台侧健康度（小程序后台"运维中心"：启动耗时、JS 错误率、白屏率）
```

### 三个公共字段

**【专题补写】** 小程序端要在上面这套规范上强制加三个公共字段，否则后面的增长分析做不了：

```javascript
{
  // 1. 来源场景：小程序的增长几乎全靠"从哪进来"，这是最关键的一维

```

```javascript
// utils/track.js
let common = {};
function init(ctx) { common = { ...ctx }; }        // onLaunch 时注入 scene/entryPath

    wx.request({ url: 'https://api.example.com/track', method: 'POST',
```

> 来源：`../super-individual/app-publishing-guide/common/analytics.md:418-427`

**【专题补写】** 原文这五条是从 App 提交审核的角度写的，但对小程序同样成立，且有一个运维侧的执行难点：**声明要跟着埋点走，而埋点会改**。做法是把埋点表当成声明的唯一来源：

```bash
# 每加一个事件或字段，同步更新两张表，否则政策文本必然失真
埋点字段表（仓库里维护，字段｜类型｜用途｜保留期｜是否传第三方）
   ↓ 每次发版前 diff 一次
隐私政策的"收集哪些数据"清单 + 微信后台"用户隐私保护指引"
```

三处口径必须一致：隐私政策页、微信后台填的隐私接口声明、代码里实际上报的字段。不一致时平台侧会直接拒绝对应接口调用（授权代码见 [02-development.md](./02-development.md)，政策文本的写法与八要素见 [06-legal.md](./06-legal.md)，本篇只管"埋点变更时怎么让它不失配"）。

```bash
# - 下载 → 注册
# - 注册 → 首次使用
# - 首次使用 → 付费
# - 付费 → 复购
```

> 来源：`../super-individual/app-publishing-guide/common/analytics.md:360-393`

**【专题补写】** 小程序没有"下载"这一步，把漏斗换成小程序版本：

```bash
曝光 → 进入（场景值决定这一步的转化率）
进入 → 完成首屏（首屏耗时决定）
完成首屏 → 关键行为（一次有效使用，你的 aha 动作）
关键行为 → 次日回访（留存）
次日回访 → 付费
付费 → 复购/续费
```

单人项目只需要每天看五个数，多了看不过来：

```bash
1. 新增进入用户数（并按 scene 拆到入口）
2. 次日留存率
3. 关键行为完成率
4. 付费人数与金额
5. 后端接口错误率 + 平台侧 JS 错误率
```

第 5 项是健康度，前 4 项是增长。健康度异常时先别看增长。

## 崩溃与异常

原文的 Crash 监控方案面向原生 App，只列不搬：Firebase Crashlytics、Bugly（腾讯，国内数据准确、支持 iOS/Android、需符号表配置）、网易 BugLens。

> 来源：`../super-individual/app-publishing-guide/common/analytics.md:327-358`

**【专题补写】** 小程序没有"崩溃"，有"错误"，且多数错误不会终止进程而是白屏或功能静默失效——更危险，因为你收不到通知。四类要各自有抓手：

```bash
1. JS 运行时错误   → 平台"运维中心 → JS 错误"，会给你错误堆栈和版本维度
2. 未捕获的 Promise → wx.onError 只覆盖同步错误，异步要自己兜
3. 接口错误         → 在你自己的 request 封装里统计，不要只看后端日志
4. 白屏/启动慢      → 平台性能监控 + 真机弱网实测
```

```javascript
// app.js —— 全局错误兜底，这是小程序版的"崩溃监控最小实现"
App({
  onError(err) {
    report({ type: 'js_error', msg: err, ua: wx.getSystemInfoSync() });
  },
  onUnhandledRejection(res) {
    report({ type: 'unhandled_rejection', msg: res.reason });
  },
  onPageNotFound(res) {
    // 分包加载失败/路径变更后的老链接进来会命中这里
    report({ type: 'page_not_found', path: res.path });
    wx.redirectTo({ url: '/pages/index/index' });   // 兜底跳首页，别留白屏
  },
  onLaunch() {
    const update = wx.getUpdateManager();   // 新版发布后强制旧缓存更新
    update.onUpdateReady(() => update.applyUpdate());
  }
});

// request 封装内统一统计，接口错误率自建看板的第一指标
function request(opts) {
  const t0 = Date.now();
  return new Promise((resolve, reject) => {
    wx.request({
      ...opts,
      success: (res) => {
        report({ type: 'api', url: opts.url, code: res.statusCode,
                 ms: Date.now() - t0, ok: res.statusCode < 400 });
        res.statusCode < 400 ? resolve(res) : reject(res);
      },
      fail: (err) => {
        report({ type: 'api', url: opts.url, ok: false,
                 msg: err.errMsg, ms: Date.now() - t0 });
        reject(err);
      }
    });
  });
}
```

## 故障分级与单人 On-Call

分级、时限、升级路径这三样，仓库里的团队故障手册写得比任何小程序资料都清楚，结构可以直接借。

```bash
# P0-P4定义标准（原文）
| 等级 | 定义 | 影响范围 | 响应时间 | 恢复目标 | 升级路径 |
| P0 | 全站不可用/数据丢失 | 全部用户 | 5分钟内 | 30分钟 | 立即通知CTO/CEO |
| P1 | 核心功能不可用 | >30%用户 | 15分钟内 | 1小时 | 15分钟通知技术VP |
| P2 | 重要功能降级 | 10-30%用户 | 30分钟内 | 4小时 | 30分钟通知总监 |
| P3 | 非核心功能异常 | <10%用户 | 2小时内 | 24小时 | 次日通知Team Lead |
| P4 | 体验问题/边缘Case | 极少用户 | 下一工作日 | 下一迭代 | 工单跟踪 |
```

> 来源：`../management/specialized-guides/incident-management-guide.md:13-21`

```bash
# 升级路径设计（原文）
- **一级响应**：On-Call工程师（5分钟内确认）
- **二级升级**：15分钟未解决 → 升级至Team Lead + 相关领域专家
- **三级升级**：30分钟未解决 → 升级至总监 + 启动War Room
- **四级升级**：1小时未解决 → 升级至VP/CTO + 启动对外通报
- **原则**：升级不等于追责，是为了获取更多资源和决策权
```

> 来源：`../management/specialized-guides/incident-management-guide.md:23-28`

```bash
# 完整响应链路（原文"黄金30分钟"）
发现(0-5min) → 确认(5-10min) → 止血(10-30min) → 修复(30min-4h) → 复盘(24-72h)
```

> 来源：`../management/specialized-guides/incident-management-guide.md:64-66`

**【专题补写】** 照抄会卡在两处：升级路径上没有别人可升级，P0 的 30 分钟恢复目标你做不到。改成单人能执行的形式：

| 等级 | 小程序里的实际形态 | 单人响应目标 | 单人止血目标 | 判断依据 |
|---|---|---|---|---|
| P0 | 后端整体不可用、数据丢失、支付回调不处理 | 见到就处理，别的事全放下 | 1 小时内止血（不是修好） | 订单或收入在受损，用户打开就是错 |
| P1 | 核心链路挂：下单、登录、分享 | 当天 | 4 小时内止血 | 关键行为完成率断崖 |
| P2 | 重要功能降级：搜索、导出、图片加载 | 当天 | 当日或次日 | 有兜底可绕，体验明显劣化 |
| P3 | 非核心异常：某页面样式、埋点漏报 | 本周 | 随下个版本 | 不影响转化 |
| P4 | 边缘 case、优化项 | 记下来就走 | 排进迭代 | 只有个别设备或版本 |

与团队表的差别：**响应时间收紧**（只有你一个人，没有"次日通知"这一档），**恢复目标放宽**（没有第二个人可以调资源）。原文的"升级"在单人语境里换成两条真实动作：

```bash
15 分钟定不了根因 → 停止排查，直接执行止血（关开关 / 降级 / 限流，见"回滚与止血"）
1 小时止不住血   → 升级对象换成外部：云厂商工单、平台侧反馈、支付渠道客服
                   这一步别省。单人项目的故障常常卡在第三方（证书、CDN、回调）
```

**【专题补写】** 还有一个决定要显式做出来：**你是否 7×24**。原文的 On-Call 体系假设有人轮班，单人没有，所以要么明说不做，要么用机制顶替人值守。

```bash
1. 告警只发手机，且只发 P0/P1（阈值见下一节）；P2 及以下次日处理，写进给自己的约定
2. 唯一需要接近实时的场景是支付回调 → 把它做成"可重试 + 有对账 + 有延时告警"，
   用机制保证钱不出错，而不是靠人半夜起床
3. 别把"响应快"当成目标。单人的可持续性来自故障少，不是来自熬夜
```

## 告警治理与运维度量

```bash
# 告警疲劳（原文，在"心理健康"小节下）
- **告警疲劳**：每月告警数 > 50条需治理，目标 < 20条可操作告警
- **轮换保护**：连续处理2次P0后强制休息1天
```

> 来源：`../management/specialized-guides/incident-management-guide.md:55,57`

**【专题补写】** 这一条对单人比对整个团队更要紧：团队可以把噪声分给五个人轮掉，你只能全部自己消化。一个月 50 条噪声告警的必然结果是你开始不看手机，然后 P0 也跟着漏。所以上一节给的阈值要**按"每月总告警数 ≤ 20 条"倒着调**——超了就提高阈值或加抑制窗口，而不是要求自己更警觉。

```bash
# 单人告警的最小治理手段，四项都不需要额外系统
1. 分级：只有接口错误率与白屏率两项发即时通知，其余进看板次日看
2. 抑制：同一告警 30 分钟内不重复。重复不增加信息，只训练你忽略它
3. 静默：已知维护窗口手动静默，别让它进本月统计
4. 每周日 10 分钟把本周告警标一遍（真故障 / 噪声 / 已知）
   噪声占比 > 50% 说明阈值定错了，当场改阈值
```

```bash
# 核心指标（原文）
| 指标 | 定义 | 目标 |
| MTTD（平均发现时间） | 故障发生到被发现的时间 | < 5分钟 |
| MTTR（平均恢复时间） | 故障发现到恢复的时间 | P0 < 30分钟 |
| MTBF（平均故障间隔） | 两次故障之间的平均时间 | 逐季提升 |
| 变更失败率 | 导致故障的变更占比 | < 5% |
| 告警准确率 | 真实故障 / 总告警数 | > 80% |
```

> 来源：`../management/specialized-guides/incident-management-guide.md:277-283`

**【专题补写】** 五个数记不住，也不必。留两项，这两项直接决定你该把下一步投在监控还是投在功能上：

```bash
发现时间   ← 只用一个问题衡量："这个故障是我先看到的，还是用户先告诉我的？"
            后者占多数就说明现有监控等于没有，优先补告警
变更引起比 ← 每次复盘标一行"是否由变更引起"（原文 :82 的经验值是 80%）
            这个比例高于 50%，问题在发布流程（缺开关、缺灰度），不在基础设施
```

原文的 MTTR 在小程序语境里要拆开：**止血时间能做到分钟级（靠开关），恢复时间做不到（版本回退要重新审核）**。所以记"止血用了多久"，不要记 MTTR，否则数字永远难看且不可比。

```bash
# 成熟度评估（原文）
  - Level 1：被动响应（救火）
  - Level 2：有流程（On-Call + 复盘）
  - Level 3：主动预防（监控 + 混沌工程）
  - Level 4：自愈系统（自动检测 + 自动恢复）
  - Level 5：持续优化（数据驱动 + 预测性维护）
```

> 来源：`../management/specialized-guides/incident-management-guide.md:293-298`

**【专题补写】** 单人项目的合理目标是稳定停在 Level 2，个别动作够到 Level 3。Level 3 的混沌工程和 Level 4 的自愈系统不要碰——它们的前提是你对基础设施有控制权，而小程序的前端在平台手里。最划算的一跳是 Level 1 → Level 2，成本只有两样：告警分级、四行复盘。

### SLO 与错误预算

```bash
- **SLI（服务等级指标）**：可量化的服务指标
  - 可用性：成功请求数 / 总请求数
  - 延迟：P99响应时间
  - 吞吐量：每秒处理请求数
  - 正确性：返回正确结果的比例
- **SLO（服务等级目标）**：内部目标（通常严于SLA）
  - 示例：可用性 99.95%（月度）= 每月允许21.6分钟不可用
- **SLA（服务等级协议）**：对外合同承诺（违反有赔偿）
  - 示例：可用性 99.9%，低于则赔偿10%月费
```

> 来源：`../management/specialized-guides/incident-management-guide.md:134-143`

```bash
- **计算**：1 - SLO = 错误预算（99.95% SLO → 0.05%预算）
- **用途**：
  - 预算充足 → 可以激进发布新功能
  - 预算耗尽 → 冻结发布，专注稳定性
- **协商**：与产品团队共享Error Budget仪表盘，用数据平衡速度与稳定性
```

> 来源：`../management/specialized-guides/incident-management-guide.md:146-150`

```bash
- **原则**：SLO不是技术团队单方面决定，需要产品确认"用户可接受的体验"
- **方法**：从用户旅程出发定义关键路径，不同路径不同SLO
- **示例**：支付页面 99.99%，推荐列表 99.9%，后台报表 99.5%
```

> 来源：`../management/specialized-guides/incident-management-guide.md:153-155`

**【专题补写】** 单人项目要 SLO 只有一个理由：**它给你一个"什么时候停止加功能、先修稳定性"的客观依据**，否则你永远不会主动停。原文那句"不同路径不同 SLO"是这一节对你最有用的一条——别给所有接口定同一个目标。落地成三步：

```bash
1. 挑一条最关键路径。小程序里通常是"进入 → 看到内容 → 能付费"，
   只对这条路径上的接口定目标，其余不定（定了也守不住，还制造噪声）
2. 定一个你守得住的月度值。起步参考：核心接口可用性 99.5%（月内约允许 3.6 小时不可用）
3. 换算成"这个月已经用掉多少"。用完了就冻结新功能发布，只做稳定性——
   这是原文 :149 那条规则在单人身上的唯一形态：没有别人会来冻结你，只能靠这个数字
```

99.5% 与 3.6 小时是自拟起步值，按收入对这条路径的依赖度调：付费完全经过你的接口的，目标定高；只靠流量主广告变现的，短时间不可用的金钱损失接近于零，可以定松。原文 "SLO 需产品确认用户可接受的体验" 在单人语境里就是问自己一句：**用户打不开你的小程序时，他会等还是会走**——走掉且不再回来的比例有多高，决定这个数该定多严。

## 灰度与发布节奏

小程序没有 App 那种按比例分阶段放量的开关。原文记录的平台侧发布流程只有一档：审核通过后点"发布"，然后等待全量发布（约几分钟）。**所以灰度必须在你的服务端做**。

```bash
# 审核通过后：
# 1. 在版本管理中点击 "发布"
# 2. 确认发布
# 3. 等待全量发布（约几分钟）
```

> 来源：`../super-individual/app-publishing-guide/mini-program/wechat.md:336-341`
> 政策快照｜截至 2026 年 10 月。平台是否提供分阶段放量能力会调整，发布前请核对官方文档，以官方为准。

```bash
# 摘自变更管理原则
- 修复方案：制定方案 → 评审 → 灰度验证 → 全量
- 改进项示例：灰度发布覆盖配置变更
```

> 来源：`../management/specialized-guides/incident-management-guide.md:90,128`

**【专题补写】** 小程序版灰度落地做法：

```javascript
// 后端下发配置，客户端按配置分支。这是唯一能"秒级回滚"的手段。
// GET /config  返回：
{
  "version": "2026-10-06-1",
  "features": {
    "newCheckout": { "enabled": true, "rollout": 0.05, "whitelist": ["uid_1"] },
    "aiSummary":   { "enabled": false }
  },
  "fallbackText": "服务繁忙，请稍后再试",
  "killSwitch": false
}
```

```javascript
// 客户端按 uid 取模，保证同一用户命中同一分支（体验不能跳变）
function isInRollout(uid, ratio) {
  if (ratio >= 1) return true;
  if (ratio <= 0) return false;
  let h = 0;
  for (const c of String(uid)) h = (h * 31 + c.charCodeAt(0)) >>> 0;
  return (h % 10000) / 10000 < ratio;
}
```

### 四类故障案例对照

```bash
### 案例一：数据库主从切换故障
- **现象**：主库OOM触发自动切换，新主库延迟30秒，部分写入丢失
- **根因**：大事务导致主库内存暴涨；从库复制延迟未监控
- **改进**：大事务拆分、复制延迟告警（>5秒）、应用层重试机制

### 案例二：CDN故障
- **现象**：CDN供应商节点异常，静态资源404，页面白屏
- **根因**：单一CDN供应商、无回源降级策略
- **改进**：多CDN互备、本地缓存兜底、CDN健康检查自动切换

### 案例三：配置推送事故
- **现象**：配置中心推送错误配置，全量服务同时生效，核心接口500
- **根因**：配置变更无灰度、无校验、无快速回滚
- **改进**：配置灰度推送（1%→10%→100%）、配置Schema校验、一键回滚

### 案例四：容量不足
- **现象**：大促流量超预期3倍，服务雪崩
- **根因**：容量评估基于历史数据未考虑营销爆发、无弹性扩容
- **改进**：大促前压测（目标2倍峰值）、HPA自动扩容、限流预案
```

> 来源：`../management/specialized-guides/incident-management-guide.md:254-272`

**【专题补写】** 这四条原文按团队基础设施写的，翻成小程序语言，四条全部成立且成本都不高：

| 原案例 | 在小程序里长什么样 | 你该做的那一条改进 |
|---|---|---|
| 一 · 主库切换 | 云开发/托管数据库瞬时抖动，写入静默失败；用户点了没反应 | 所有写接口做**幂等 + 应用层重试**（同一请求带唯一 id，后端去重） |
| 二 · CDN 故障 | 图片全挂 → 白屏。**这是小程序最典型的平台侧看不出来的故障**：JS 无错误、接口全 200 | 图片走可回源的路径；关键图（首屏、支付二维码）留 base64 或接口内联兜底 |
| 三 · 配置推送 | 后端改了 `/config` 字段名，小程序读不到 → 功能静默失效 | 配置加 **Schema 校验** + 客户端读不到新字段时用默认值而不是崩；灰度阶梯 1%→10%→100% |
| 四 · 容量不足 | 被一条视频带火，流量瞬时几十倍，接口排队雪崩 | 限流优先保**下单与支付**，牺牲列表页；云开发自动扩容优于提前压测 |

案例三那句"配置变更无灰度、无校验、无快速回滚"与上面 1%→10%→100% 的阶梯是同一类改进，原文在两处分别记过（`:128`、`:267`）：**这个阶梯不是本文保守拟定的经验值，是复盘产出的改进项**。

发布节奏 SOP：

```bash
第 0 步  新功能默认 enabled=false 上线（代码先上，开关后开）
第 1 步  自己 + 种子用户白名单验证 1 天
第 2 步  rollout 1% → 观察接口错误率与 JS 错误率（至少 2 小时）
第 3 步  rollout 10% → 观察一个完整日内周期
第 4 步  rollout 50% → 确认业务指标（转化率）不劣化
第 5 步  rollout 100%，一周后清理旧分支代码
回滚手段：任何一步异常 → rollout 改 0，秒级生效，不用发版
```

需要平台审核才能生效的是**代码**，不需要的是**配置**。把这个边界当成设计原则：能放后端的判断都放后端。

## 回滚与止血

```bash
# 后台操作：
# 1. 版本管理 → 开发版本
# 2. 选择历史版本
# 3. 提交审核
# 4. 发布
```

> 来源：`../super-individual/app-publishing-guide/mini-program/wechat.md:645-653`

**【专题补写】** 小程序回滚 = 重新提审，不是止血手段。真实的止血优先级（改自原生故障响应原则"回滚 > 降级 > 限流 > 切流"，来源 `incident-management-guide.md:79-86`）：

```bash
1. killSwitch / rollout 置 0     ← 秒级，唯一真快的招，前提是功能有开关
2. 后端降级返回（兜底数据、静态文案） ← 秒级
3. 限流（保护核心链路，牺牲非核心）    ← 分钟级
4. 前端热修                        ← 不支持，别指望
5. 版本回退                        ← 小时级（要审核）
决策原则：5 分钟内定不了根因，先关开关（来源同上 :86）
```

## 故障复盘

```bash
# 复盘要求（原文）
- 复盘在故障后 24-72 小时内进行
```

> 来源：`../management/specialized-guides/incident-management-guide.md:94-95`

单人项目别做重型复盘，固定四行就够：

```bash
现象：用户/指标看到了什么（写数字，不写"体验不好"）
触发：哪个变更/哪次外部事件
止血：实际用了哪一招，花了多久
改进：一条能落地的（写开关名/校验点，不写"加强意识"）
```

复盘产出的"改进"要落成上面"灰度与发布节奏"里的开关或自检项，否则同一次故障会重演。

### 什么时候升级到重型复盘

原文的复盘标准比"四行"重得多，先把原文照录，再说明单人怎么用。

```bash
### 无责复盘文化
- **核心理念**：人会在任何系统中犯错，目标是让系统更健壮
- **禁止**：指名道姓追责、"谁干的"、"为什么没检查"
- **鼓励**：描述行为和系统缺陷、"流程哪里允许了这个错误发生"
- **领导示范**：管理者先分享自己的失误，建立心理安全
```

> 来源：`../management/specialized-guides/incident-management-guide.md:159-163`

```bash
问题：用户无法支付
Why1：支付网关超时
Why2：数据库连接池耗尽
Why3：慢查询占用连接未释放
Why4：新上线的报表查询未加索引
Why5：代码审查未覆盖SQL性能 + 缺少慢查询告警
改进：①SQL Review Checklist ②慢查询自动告警 ③连接池监控
```

> 来源：`../management/specialized-guides/incident-management-guide.md:166-174`

```bash
# Action Items管理（原文）
- **格式**：具体行动 + 负责人 + 截止日期 + 验收标准
- **跟踪**：录入项目管理工具，下次故障周会Review
- **闭环**：超期未完成的Action Item自动升级至总监
- **有效性验证**：改进措施实施后，验证是否真正降低了同类故障概率
```

> 来源：`../management/specialized-guides/incident-management-guide.md:187-191`

**【专题补写】** 本文件前面写的"单人项目别做重型复盘"与原文的 24-72 小时复盘、5-Why、Action Item 闭环并不矛盾，差别在**按等级分档**：

```bash
P3/P4   四行，或者只记一条改进，甚至允许不记（不值得占你半天）
P2      四行 + 一条改进落成开关或校验点，当天做完
P0/P1   四行 + 5-Why 追到"哪道流程允许它发生" + 改进写成带截止日期的 Action Item
        且这类故障的时间线要留档（原文 :176-185 的三列时间线），
        理由不是复盘好看，是向云厂商或支付渠道提工单时举证要用
```

两条原文要求对单人同样成立，不要因为"就我一个人"而省：

- **无责复盘**。单人最容易犯的恰恰是指名道姓追责自己（"我怎么忘了加校验"）。换成系统口径才有产出：写"发布自检清单里没有这一项"，下次清单就会多一项；写"我蠢"，下次还是忘。
- **Action Item 要有截止日期和验收标准**。原文的"超期升级到总监"在单人语境里没有对应物，替代做法是把改进项当成一个有截止日的任务进你的待办，超期就自己看到——单人项目最大的故障来源正是"复盘时说好了要加开关，然后没加"。

## 成本

基础设施的选型、配额与价格档位在 [02-development.md](./02-development.md) 的"后端与云开发"一节统一记录（原文出处 `../super-individual/app-publishing-guide/toolchain/backend.md:354-405`），本篇不重复数字，只补运维视角的三件事：钱花在哪些项上、什么时候突然变多、怎么提前知道自己超了。

**【专题补写】** 小程序特有的成本项与原生 App 不同，注意三项：

```bash
1. 无应用商店分成，但有支付手续费 → 见 ./05-monetization.md
2. 云开发按量计费随 DAU 上涨，验证期便宜、放量后要重新算账
3. CDN 与图片存储往往是小程序最大的基础设施开销
   （小程序包体限制把图片都推到了 CDN，访问量一大就是带宽费）
```

### 账单项与观察点

| 成本项 | 计费方式 | 什么时候突然变多 | 运维侧看什么 |
|---|---|---|---|
| 后端计算 | 云开发按量 / 主机固定 | 一次爆款流量，或被脚本刷接口 | 每分钟请求数、单请求平均耗时 |
| 数据库与存储 | 容量 + 读写次数 | 埋点直接写业务库、缺索引导致全表扫 | 慢查询次数、读写单元消耗量 |
| CDN 与出口带宽 | 按流量 | 图片被外链盗刷、首屏图未压缩 | 日带宽峰值、缓存命中率 |
| 短信与第三方接口 | 按次 | 验证码无频控被刷 | 单接口日调用量、调用集中度 |
| 支付手续费 | 按成交额百分比 | 成交额上涨（好事，但要算到手） | 见 [05-monetization.md](./05-monetization.md) |
| 认证与备案 | 年费或一次性 | 不随量变化 | 见 [06-legal.md](./06-legal.md) |

**【专题补写】** 单人项目最容易失控的是第二、三行，而两行的解法都不花钱：

```bash
埋点 → 不要进业务库。先落文件或对象存储，每天批量入一次分析表
       前端上报允许失败，业务写入不允许，两者绝不共用一套连接与配额
图片 → 上 CDN 并开防盗链与频次限制；首屏图按必需尺寸压缩（尺寸规范见 01）
       命中率低的典型原因：URL 带随机参数，把 CDN 缓存打穿
```

**【专题补写】** 云厂商的余额与消费提醒要开，阈值设在"预计当月超额"而不是"余额归零"：欠费停服对小程序是 P0，而恢复动作（充值、解除锁定）通常比修一个 bug 慢得多，且期间你的小程序是整站不可用。

月度成本与收入放在一起算，见 [05-monetization.md](./05-monetization.md) 的"成本与现金流"。

### 加速审核与发布节奏

原文只留了一句"部分情况可申请加速，如重大活动、安全问题等"，加速的具体入口、次数额度、适用条件仓库尚未覆盖。**因此把加速审核当成计划外资源，而不是排期手段**：能提交加速的场景通常由平台判定，而"我明天要上线"不在其中。

**【专题补写】** 单人项目对审核周期的正确应对是把它写进发布节奏，而不是指望加速：

```bash
1. 有硬上线日的事，按"审核周期 + 一次被拒重提"倒推提审时间
   也就是说：目标日期往前推至少两个审核周期提交，而不是一个
   各平台审核周期的具体数字与拒审处置流程统一记在 ./02-development.md
2. 线上出问题时先止血，不要靠"发个修复版 + 申请加速"
   服务端开关与配置下发的响应速度永远快于审核（见"运维对象与边界"四项清单）
3. 把提审变成固定节拍（例如每周一次批量提审），
   而不是每个改动独立提审——后者会把你的节奏变成"随时在等审核"
4. 加速入口若存在，通常在小程序后台的版本管理或提审流程内，
   是否可见取决于主体类型与类目；找不到入口就当成没有
```

> 政策快照｜截至 2026 年 10 月。审核时长、加速资格与额度都以提审页面当时显示的信息为准，发布前请核对官方文档，以官方为准。
